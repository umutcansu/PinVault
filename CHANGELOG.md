# Changelog

## Unreleased — Vault files behind the screen lock, configs that expire

### Library

- **`userAuth(UserAuth.REQUIRED | IF_SCREEN_LOCK)` on a vault file.** The stored copy is sealed with the device's user-auth RSA key (Android Keystore, StrongBox when available), which the hardware uses only after the user passes the screen lock or a strong biometric; content is AES-256-GCM under a fresh key bound to the file name. Before, any code running as the app — a hooked process on a rooted phone — could open every stored file through the app's own Keystore keys. Fetch and sync need no prompt. `PinVault.unlockFile(activity, key, prompt)` (suspend, and a callback overload) shows the system prompt and returns `VaultFileUnlockResult` (`Unlocked | NotFound | Cancelled | Invalidated | Failed`); `isFileLocked(key)`; `loadFile` returns `null` for a sealed copy. `VaultFileResult.Updated.bytes` and the update listener's copy are empty for a locked file. Without a screen lock, `REQUIRED` refuses to store (`VaultFileResult.Failed` with `ScreenLockRequiredException`) and `IF_SCREEN_LOCK` stores as before, sealing once a lock exists. Files stored before `userAuth` was set are sealed on first read.
- **`encryption(VaultFileEncryption.USER_AUTH)`** (server value `user_auth`, needs `userAuth`): the server seals the file for the device's user-auth key, so the content never reaches the app before the prompt. The device registers that key with `POST …/vault/devices/{deviceId}/public-key` and `"purpose": "user_auth"` (same proof rules as the per-device key; the replacement proof now also takes a `user_auth` file's token) at init and before the next fetch after a new key; a `412 user_auth_key_required` registers again and retries once. The envelope is stored as it came and decrypted, then signature-checked, in `unlockFile`; a copy that fails is deleted. Only a server-sealed copy is accepted for such a file: anything else in storage (an open or locally sealed blob, one without the prefix) is deleted unread and `unlockFile` returns `Invalidated`; `loadFile` never returns content for it; a copy whose Config API is unknown is not opened (no signature check, fail closed). New `CertificateConfigApi.registerUserAuthPublicKey(deviceId, publicKeyPem, attestationChain)` (default no-op). A custom implementation compiled against 2.1.1 or earlier lacks it (no `-Xjvm-default`, so the call ends in `AbstractMethodError`); PinVault catches that and fails `user_auth` files with a reason saying the backend does not support them.
- **Android key attestation for the user-auth key.** The key is generated with `setAttestationChallenge(SHA-256("pinvault-user-auth-key:v1:" + deviceId))` — StrongBox with attestation, then the TEE with attestation, then the TEE without — and every user-auth registration sends `"attestationChain": [base64 DER, leaf first]` (none when the device cannot attest; older servers ignore it). Refusals map to `VaultFileResult.Failed` with a reason: `409 user_auth_key_exists` (an administrator must reset the device's user-auth key), `403 attestation_required`, `403 attestation_invalid` (with the server's reason). **What this protects:** root running as the app gets only sealed copies ONLY when the server enforces the attestation (`USER_AUTH_ATTESTATION=enforce` + the app's package name; locked bootloader). Without enforcement the first key a device registers is trusted (trust on first use), so a rooted app's credentials can register a software key on a first registration; replacing a registered key needs the device's credential (client certificate or vault token) together with a passing attestation — which counts only when the server binds the app's package name AND signing certificate — or an admin reset.
- **Copies are stamped with the key the server sealed for.** The key id the library last registered successfully with each Config API is persisted (inside `pinvault_secure_vault_files.xml`) and stamped on each `user_auth` copy. A copy sealed for another key is given up (`Invalidated`) and the next fetch registers again and downloads it again, instead of answering "already current" for ever. Key creation + registration run under a lock, so init's registration and an early `fetchFile` cannot race. A padding failure on unwrap after a passed prompt (the copy was sealed for another key) deletes the copy, forgets that Config API's registration and returns `Invalidated`.
- **Key kinds, and what retires each.** Android 11+: every unlock asks (strong biometric or screen lock). That key is authorised by `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`, which binds it to the screen lock: only removing the screen lock retires it; enrolling or deleting a fingerprint or face does **not** (that invalidates biometric-only keys). Android 7–10 with a strong fingerprint at key generation: a per-use, fingerprint-only key — the one biometric-only kind — retired by a new fingerprint, by removing all fingerprints or by removing the screen lock. Otherwise a 10-second screen-lock key, opened by the prompt or a phone unlock, retired only by removing the screen lock. (KDoc and README said a new fingerprint retires the Android 11+ key; corrected.) The reference server refuses time-bound keys from Android 11+, and from every version with `USER_AUTH_REQUIRE_PER_USE=true`: on Android 7–10 without a strong fingerprint a `USER_AUTH` file then fails with the server's reason. `VaultFileUnlockPrompt.negativeButtonText` (default "Cancel") for the fingerprint-only prompt.
- **Only a retired or missing key** makes a new key; it, a copy sealed for another key, or a copy of the wrong kind deletes a stored copy. Any other Keystore error returns `Failed` and keeps both. "Sealed for another key" is read narrowly: an `IllegalBlockSizeException` / `BadPaddingException` with no cause, or one whose cause is the Keystore's exception with `INVALID_ARGUMENT` (-38). The Android Keystore wraps nearly every failure in an `IllegalBlockSizeException`, and any of them used to delete the copy and the registration after a passed prompt.
- **Stored configs expire.** `expiresAt` is stored with the config. Past it, `init` fails with the new `ConfigExpiredException` when no fresh config can be fetched, and pinned clients refuse handshakes until one arrives (the request then refetches and retries). Before, blocking the Config API kept a device on its last pins forever. `PinVaultConfig.Builder.expiredConfigGrace(amount, unit)` (default 0) trades that for availability. Configs of unsigned blocks stored by 2.1.1 or earlier get 7 days from the first start of this version (written down, restarts do not extend it), whatever their `issuedAt`: 2.1.1 did not write `issuedAt` back for unchanged pins. (A signed block's 2.1.x config is discarded instead, see "The stored config is verified when it is read".) The client `getClient()` hands out follows a freshness write-back (it reads the live config), so a renewed `expiresAt` takes effect without a restart. `getClient(settings)` clients have no recovery interceptor and stop at expiry unless periodic updates (or `updateNow()`) run. Expiry is also checked on every request, not only at the handshake (see "Open connections follow the pins"). A fetch with the same pins now writes the newer `issuedAt`/`expiresAt` back. The periodic worker refreshes every Config API, not only the first.
- **Rollback keeps the replay checks.** A config rolled back after a failed health check no longer lowers the stored `issuedAt` or per-host version watermarks; exactly that config may be applied again. A host the server drops keeps its version watermark too (it used to be forgotten: drop the host, add it again at any version).
- **Refused: configs that would lock a device out** — `issuedAt` more than 1 hour ahead of the device clock (a slow clock must not lose every config), an `expiresAt` already in the past (a custom `CertificateConfigApi` can hand one over; the stored config is kept), a validity window over 30 days or an `expiresAt` more than 30 days from now (the window was not checked for a config without `issuedAt`), a per-host version jump over 1,000,000, a first version over 1,000,000 for a host the device has not seen. A signed config without `issuedAt` or `expiresAt` is refused.
- **`PinVaultConfig.Builder.requireCaTrust(vararg hostPatterns)`**: for those hosts the chain must match a pin and also pass the platform's CAs (network security config included). Compiled in; the server cannot turn it off. A refusal is `CaTrustException` and is not retried. A wildcard with a port (`*.example.com:443`) now matches that port, for pins as well (it never matched before, so such a CA requirement was silently skipped).
- **Open connections follow the pins.** The pin check and the config's expiry ran only in a full TLS handshake, so an HTTP/2 or keep-alive connection, or a resumed TLS session, stayed trusted after its pin was removed or the config expired. Every client the library builds or configures (`getClient()`, `getClient(settings)`, `applyTo`, the Config API's own client) now has a network interceptor that checks the connection's certificates (from the TLS session) against the live config for the request's host and port, and the config's expiry plus grace, before each request; a failure is an `SSLHandshakeException` with the same `CertificateException` cause as a failed handshake, and the connection is closed. On every pin change the socket factories get a fresh `SSLContext` (no session to resume) and the pooled connections of all library-built clients are closed, `getClient(settings)` clients included. `applyTo` clients keep their own pool; the per-request check is their protection.
- **The stored config is verified when it is read.** A signed block stores the signed envelope (payload and signatures) with the config, verifies it at every load against the keys trusted now, and uses the config inside it; stored fields rewritten on the device no longer survive. A stored config that does not verify is discarded: `init` fetches a fresh one or returns `Failed` (`NoConfigAvailableException`, the reason says so). **Upgrade:** a signed block's config stored by 2.1.x has no envelope and is discarded, so the first start after the upgrade needs the Config API once. Unsigned blocks, static pins and custom APIs without `SignedConfigSource` have no envelope and no at-rest integrity.
- **Change detection compares hosts, versions, pin hashes and mTLS flags**, not versions alone: a pin removed without a version bump is applied when the config's `issuedAt` is newer (unsigned blocks: whenever it differs). Different content at or below the stored `issuedAt` is still refused as a replay.
- **A custom `CertificateConfigApi` no longer bypasses signature verification.** New `api.SignedConfigSource` (`fetchSignedConfig(currentVersion)`, `fetchScopedSignedConfig(...)` with a default): a custom API that implements it hands over the signed envelope and the library verifies it like its own client's. **Breaking:** a block with signing keys and a custom API that does not implement it makes `init` return `Failed`, unless the block calls `allowUnsigned()` (stored on the block as `ConfigApiBlock.allowUnsigned`). `signingStatus()` is non-null for a custom API that implements it.
- **`ConfigApiBlock.Builder.serverScope(id)`**: the signed payload must carry `"configApiId": "<id>"` or the config is refused (fetched and stored). Not set: unchanged. Exposed as `ConfigApiBlock.serverScope`.
- **Host names and pins are validated; the store is JSON.** Every config (fetched, static, custom API) is refused as a whole unless each host name is letter-digit-hyphen labels with an optional single leading `*.` and an optional `:port` (1–65535), at most 253 characters, no wildcard directly under a public suffix (`*.com`, `*.co.uk`; a built-in list, not the full PSL), no duplicates; pins must be 44-character Base64 SHA-256. **Breaking:** IPv6 literals and names with underscores are refused; static pins with placeholder hashes make `init` fail. Pins and version watermarks are stored as JSON; the old `|`/`,`/`=`/newline format (in which a crafted host name became another entry) is read once, entries with invalid host names dropped, and rewritten. `mtls` and `clientCertVersion` are now stored.
- **A newer signing-key set clears the replay watermarks.** When a newer recovery-signed key set is applied, the `issuedAt` and per-host version watermarks of that Config API are cleared and a stored config the new set does not vouch for is dropped, so revoking a stolen signing key ends what it planted. Crash-safe: the key-set version the watermarks were reset for is persisted.
- **Keystore failures are not "nothing stored".** The config store and the signing-key store throw the new `StoreUnreadableException` when the Keystore cannot open an entry: the update or init fails for that attempt (nothing applied, retried next call) instead of reading the replay watermark as 0 and `expiresAt` as "never"; `SignatureTrust` no longer falls back to the compiled-in keys (which re-trusted a revoked key for the rest of the process) and reads the set again on the next use. The other stores behave as before.
- **Expiry does not follow a clock set back.** Expiry is decided by the later of the device clock and the highest time seen (persisted per Config API, at most 5 minutes behind, carried forward by the monotonic clock in a running process). The reference goes back only when a config newer than every earlier one is accepted: it becomes the later of the device clock and that config's `issuedAt`. Whether a fetched config is already expired is judged by that clock too, except for a config newer than every earlier one (the one that may correct a reference that ran ahead); whether its `issuedAt` lies ahead is judged by the device clock.
- **Recovery is bounded and updates are single-flight.** `updateNow()` runs one fetch at a time and concurrent callers share its result. The recovery interceptor checks the cooldown inside its lock, lets requests that failed together share one refetch, allows 6 refetches per 5 minutes across hosts (plus the per-host breaker), one per 5 minutes for hosts without a pin entry (`UnpinnedHostException`, new), and tracks at most 64 hosts.
- **TLS 1.3, and the client certificate goes only where it belongs.** The library's `SSLContext` is `"TLS"` instead of `"TLSv1.2"` (which capped connections at 1.2, where the client certificate is sent in the clear); every socket enables TLS 1.2 and 1.3 only, whatever the client's `ConnectionSpec`. **Behaviour change:** the default client identity is presented only to the block's Config API, enrollment and renewal listeners (host and port) and to hosts whose pin entry has `mtls = true`; hosts with a host-specific certificate get that one; no other pinned host gets a client certificate. The peer host is taken from the socket the client opened, never from reverse DNS; unknown means no pin entry and no client certificate.
- **A Config API must be https and pinned.** Enforced at `init` for blocks built any way (constructor included): `https://` for `configUrl`, `enrollmentUrl`, `renewalUrl`, and non-empty bootstrap pins, else `InitResult.Failed`; the block's client refuses TLS without pins and refuses plain HTTP (also `PinVaultBackendReporter.pinnedClient`). **Breaking for tests against `http://`:** call the new `ConfigApiBlock.Builder.allowUnpinnedConfigApi()`.
- **`PinVault.reset()` keeps the replay watermarks**, the signing-key set and the clock reference, and now clears the active config of every Config API (it cleared only the first). A config at the stored `issuedAt` is accepted while nothing is active, so a backend that serves one signature until the content changes works after a reset.
- Logs no longer contain the tail of a vault access token, the ANDROID_ID, the client certificate's CN / client id, or the server certificate's CN ("Pin verified" names the host and the pin).
- **`PinVaultConfig.Builder.wipeVaultFilesOnRevocation()`**: when the server refuses this device's identity, every vault file of that Config API is deleted, locked copies included. The `403 reenroll_required` answer is not signed, so it wipes only when it was about the identity: it arrived on a connection that presented the client certificate the block has loaded (read from the response's TLS handshake), or it is the answer to that certificate's own renewal request over the block's mTLS connection (never one from the recovery door, which asks for no certificate); once per certificate. The same answer on a connection without a client certificate (a TLS-only block, a request before enrollment) still raises the `REENROLL_REQUIRED` event and deletes nothing — it used to wipe the block's files and the user-auth key. `PinVault.unenroll(context, label, wipeVaultFiles)` does it on demand for the Config APIs that use that client certificate for mTLS (label matches and the block names an `enrollmentUrl` or `renewalUrl`, bundles a `clientKeystore`, or has a `token_mtls` file); a TLS-only block sharing the default label keeps its files.
- Enrollment refusals: `identity_already_enrolled` maps to `EnrollmentRefusal.DEVICE_ALREADY_ENROLLED`, `csr_required` to the new `CSR_REQUIRED`, `attestation_required` / `attestation_invalid` to the new `ATTESTATION_FAILED` (the server's `message`, or else its `reason`, is in `Refused.message`).
- **The enrollment key is attested.** The mTLS identity key is generated with `setAttestationChallenge(SHA-256("pinvault-identity-key:v1:" + deviceUid))` — StrongBox with attestation, then the TEE with attestation, then the TEE without — where `deviceUid` is the device id the request body carries (`deviceUid`; `deviceId` when no `deviceUid` is sent). Every CSR enrollment request (token, enrollment code, application without a code, open; and the pickup of a waiting request, with the same key) sends `"attestationChain": [base64 DER, leaf first]` when the key's leaf has the attestation extension. Before, a script, an emulator or a repackaged app holding a token enrolled exactly like a phone; a server that verifies the chain can now tell. A key generated earlier has no chain: when an enrollment is refused for attestation and the key has none, the library makes a new key and sends the request once more (never for a request that waits for approval). New `ClientIdentityKeyProvider.ensureKeyPair(attestationChallenge)`, `attestationChain()`, `attestationChallenge(deviceUid)`; new `CertificateConfigApi.enrollWithCsr(…, requestId, attestationChain)` (default: the six-argument method; a custom API compiled against 2.1.x is called through that one).
- **The verification code is 80 bits, 16 characters** (`XXXX-XXXX-XXXX-XXXX`: the first 10 bytes of SHA-256 over the key's SubjectPublicKeyInfo, Crockford base32). The 40-bit code could be matched by generating keys for a few minutes, so a stranger could have their own request approved under a waiting device's code. The first 8 characters are the old code; SHA-256("pinvault") → `0XMH-GCGP-BW6Z-10F6`. **Breaking for screens** that reserved 9 characters.
- **A key the server made is refused unless the block asks for it.** New `ConfigApiBlock.Builder.allowServerGeneratedKey()`. Without it a PKCS12 answer to a CSR enrollment is not stored, and the library no longer falls back to P12 enrollment by itself when the Keystore cannot make a key (nothing is sent; the token is not spent); both are `ClientCertEnrollmentResult.Failed` with the reason. **Breaking** for apps that enroll against a P12-only server.
- **No PKCS12 is kept in app storage.** Wherever a P12 is accepted — an opted-in enrollment, a host client certificate downloaded for an mTLS host, a bundled `clientKeystore(...)` — the private key is imported into the Android Keystore as a non-exportable key (`KeyProtection`: signing only, digests NONE/SHA-256/384/512, RSA PKCS#1 and PSS; RSA and EC) and only the certificate chain is stored. P12s stored by earlier versions are moved over on first load. Before, the key sat in the encrypted preferences as a P12 whose password is compiled into the app (`changeit` by default). Where the platform refuses the import, the P12 form is kept for that key and a warning logged. A downgrade to 2.1.x cannot read the imported form (enroll again).
- **Issued certificates are held to rules** (enrollment and renewal). A chain of one certificate is refused (it was accepted, and a later renewal then had no issuer to be checked against); the leaf's lifetime is capped by the new `maxClientCertLifetimeDays(days)` (default 825), and a stored certificate that outlives the cap is renewed at the next check; new `clientCaPins(vararg spkiSha256Base64)`: with pins the leaf must be signed directly by a certificate of the chain whose key matches a pin (without pins a renewal must still be signed by the previous issuer). Before, whoever held the enrollment or renewal listener's TLS key could answer with a 50-year leaf from a CA of their own over the device's key; the device stored it and never renewed. A stored chain of one cannot be renewed without pins (`Failed`). **Breaking** for servers that return the leaf alone or issue for more than 825 days.
- **A TLS 1.3 refusal of the client certificate reaches the recovery door.** `ClientCertRenewer.isClientCertRefusal` also takes an `SSLProtocolException` (how Android surfaces the server's post-handshake alert); a pin failure in the cause chain still does not count.
- **Vault signatures name the Config API (v2).** A block with `serverScope(id)` requires `X-Vault-Signature-V2` / `X-Vault-Signatures-V2`, signatures over `pinvault-vault-file:v2:<configApiId>:<key>:<version>:<sha256 hex>`, and verifies them with its `serverScope` — at download, at unlock of a `USER_AUTH` copy, and when the stored copy is read. Blocks without `serverScope` verify v1 as before. With v1 a file of one Config API verified for another that shared the signing key. `VaultFetchResponse` gained `signatureV2` / `signaturesV2`.
- **A vault file's version cannot jump.** A served version more than 1,000,000 above the stored one (or above zero for a first copy) is refused, the bound pin versions have. A `user_auth` envelope is stored before anything in it can be verified, and one with `X-Vault-Version: 2147483647` blocked the real file as "older" until an unlock deleted it.
- **Stored vault files are checked every time they are read.** The signatures a file was accepted with (v1 or v2) are stored with it (`pinvault_secure_vault_files.xml`) and verified again by `loadFile` / `unlockFile` with the block's keys as trusted then; a copy that fails is deleted, `loadFile` returns null, and the reason goes to the log, to `OnFileUpdateListener` (`VaultFileResult.Failed`) and to the new `PinVault.fileStatus(key)` (`VaultFileStatus`: `AVAILABLE | LOCKED | NOT_STORED | STALE | NEEDS_FETCH | INTEGRITY_FAILED | STORAGE_UNAVAILABLE`). The stored forms bind name and version into their authenticated data: the file store writes `PVF2 [version][IV][ciphertext]` with both under the GCM tag and reads the version from the file (it was a plain preferences entry), the preferences store keeps version and content in one sealed entry, a locally sealed `userAuth` copy has the version under its tag (`0x04`); earlier forms are read once and rewritten. The file store no longer deletes the existing copy when a save fails. **Upgrade:** a signed block's copy stored by 2.1.x has no signature on record — `loadFile` returns null (`NEEDS_FETCH`, nothing deleted) until one `fetchFile`, which asks for the whole file. Unsigned blocks: unchanged. Not covered: root restoring the whole storage to an earlier state (an old file with its old signature).
- **Offline lifetime.** New `VaultFileConfig.Builder.maxOfflineAge(amount, unit)` and `wipeWhenStale()`, and `PinVaultConfig.Builder.vaultFileMaxOfflineAge(amount, unit)` as the default. `loadFile` returns null (`fileStatus` = `STALE`) and `unlockFile` returns the new `VaultFileUnlockResult.Stale` once the server's last confirmation of the copy (a download or "not modified") is older than that, by the trusted clock; `wipeWhenStale()` deletes the copy then — on read, at `init` and on every periodic update. Default: no limit, as before (a revoked device that stays offline keeps its files). A copy with no confirmation on record is stale until its next fetch.
- **`PinVaultConfig.Builder.requireUnlockedDevice()`** (opt-in): keys generated from then on — identity, per-device vault key, store keys, file-store keys, imported keys — carry `setUnlockedDeviceRequired(true)` (Android 9+). Background work behind a locked screen then fails (`UpdateResult.Failed`, `VaultFileResult.Failed`, `InitResult.Failed`, `fileStatus` = `STORAGE_UNAVAILABLE`); nothing is deleted. Existing keys are unchanged.
- **`init` no longer throws when the Keystore cannot open the stores**: it returns `InitResult.Failed` (also in the callback variants, where the exception used to surface in the caller).
- **`ConfigApiBlock.Builder.clientCertHosts(...)`**: the block's client identity is presented only to its own Config API URLs (config, enrollment, renewal), to `mtls = true` pins (only while no `clientCertHosts` are listed; once they are, the list is the whole list and a signed config's `mtls = true` entry adds no host) and to hosts with their own certificate. Other hosts that expect this identity are named here (`https://host:port/` or `host:port`, port required, https only); any other host gets no certificate (`CERTIFICATE_REQUIRED`), so a pinned third party cannot collect the device's identity.
- **Each server a block points at has its own config store.** The store namespace is chosen by where the block points (`serverScope`, else the config URL): the block's existing namespace belongs to the first server it was bound to (a 2.1.x store is claimed by the current one, nothing dropped), every other server gets `<namespace>_<16 hex of SHA-256(origin)>`. Pointing a block at another server no longer inherits its watermarks ("Per-host version downgrade") and no longer wipes anything: switching away and back finds the first server's watermarks where they were (a wipe-on-change in earlier development builds let reset + switch + switch back defeat the replay guard). The trusted clock's reference stays per block. Only the app's compiled configuration decides the origin.
- **Binary compatibility — release this as a minor version (2.2.0), not a patch.** `VaultFileEncryption` gained `USER_AUTH`: an exhaustive `when` over it in app code needs a new branch. `EnrollmentRefusal` gained `ATTESTATION_FAILED` and `CSR_REQUIRED`: same for a `when` over it. `PinVaultConfig` (`vaultFileMaxOfflineAgeMs`, `requireUnlockedDevice`), `VaultFileConfig` (`maxOfflineAgeMs`, `wipeWhenStale`), `ConfigApiBlock` (`serverScope`, `allowUnsigned`, `allowUnpinnedConfigApi`, `allowServerGeneratedKey`, `clientCaPins`, `maxClientCertLifetimeDays`) and `VaultFetchResponse` (`signatureV2`, `signaturesV2`) are data classes whose constructors and `copy()` gained parameters: code calling them (rather than the builders) must be recompiled. `androidx.biometric` is an `api` dependency now. Custom `CertificateConfigApi` implementations keep working, without `user_auth` files and without sending an attestation chain; a Java implementation must add the new `enrollWithCsr` overload (delegate to `DefaultImpls`). `ClientIdentityKeyProvider` gained two methods with defaults.
- New dependency: `androidx.biometric:biometric:1.1.0` (`api`, because `unlockFile` takes a `FragmentActivity`).
- `UserAuthKeystoreTest` (instrumented, needs `-e screenLockPin`) runs the real Keystore: a PIN typed into the system prompt opens a locally sealed and a server-sealed file, a forged "prompt passed" is refused by the hardware and leaves copy and key in place, a deleted key gives the copy up. It now also checks the attestation chain (leaf first, signed in order, extension `1.3.6.1.4.1.11129.2.1.17` with this device id's challenge; skipped where the Keystore cannot attest) and that a copy wrapped for another key is given up after the PIN.
- Sample client: "Kaydı sil" now calls `unenroll(…, wipeVaultFiles = true)`; `ManualP12Store` and its README say plainly that it protects the P12 at rest only (root running as the app can unseal it; zero-overwriting a file on flash is not reliable) and that a product should enroll instead; the `user_auth` texts state the attestation condition.
- **Review fixes (2026-10-05).**
  - A Keystore fault after a passed prompt no longer deletes a good `userAuth` copy. A copy sealed on the device is never given up for an unwrap failure (only a retired key does that); a server-sealed copy only after two `UNKNOWN_ERROR` (-1000) answers in a row (what the emulator's KeyMint gives for a wrong key), never for authentication errors, -28 or -31. The count resets on save, clear and any successful unlock. A copy kept after such a failure is downloaded whole (asked as version 0) by the next fetch.
  - An enrolled certificate chain is dropped only when it does not parse or its key is gone or retired. A Keystore that fails right now (or a chain the store cannot decrypt) keeps the chain and presents no identity until the next load; an unreadable chain no longer crashes init with a `NullPointerException`.
  - A `403 reenroll_required` answer to a renewal on the recovery door (TLS, no client certificate) no longer wipes vault files; only a refusal over the block's mTLS connection that presented the current certificate does. The event is raised either way.
  - A vault file's last-confirmed time is the trusted clock's; one that lies ahead of it (more than one persist step) reads as stale until the server confirms the file again, and never deletes the copy on that ground (`wipeWhenStale`).
  - A file declared `END_TO_END` that the server serves as `plain` or `at_rest` is refused (`VaultFileResult.Failed`), as `USER_AUTH` already was.
  - A CSR enrollment advertises only `X-PinVault-Features: csr`; `p12password` is added only with `allowServerGeneratedKey()`.
  - A 2.0.x EncryptedSharedPreferences file that cannot be read at a start is kept and tried again; it is deleted only when its master key is gone or does not decrypt its keyset.
  - The enroll paths (`enroll`, `checkPendingEnrollment`, the pending pickup) read the credential store strictly: a Keystore failure returns `Failed` and sends nothing instead of looking like "not enrolled". A key under a stored certificate chain is never deleted by an enrollment answer.
  - `PinVault.reset()` and a discarded 2.1.x config keep their `issuedAt` and host versions as watermarks (a 2.1.x store had no watermark keys, so the replay guard started at zero after the upgrade). A config discarded because its envelope fails (tampered, revoked signer) leaves none.
  - Config API ids that sanitise to the same store namespace (`a.b` / `a_b`) are refused by `PinVaultConfig.Builder.build()`.
  - An app update that changes the compiled-in signing keys, their threshold or the recovery keys resets that block's replay watermarks (a fingerprint of them is stored per config store). A stolen signing key could otherwise push host versions and `issuedAt` out of reach for good on a block without recovery keys.
  - A signing-key set may carry `"configApiId"`; when it does and the block sets `serverScope`, they must match. Sets without the field are accepted as before.
  - A failed post-update health check rolls back only if the config it judged is still the live one, not a newer config a worker or the pin recovery applied meanwhile.
  - `requireCaTrust` is checked again per request with the pins (also for a host an HTTP/2 connection is reused for), not only in the handshake.
- `VaultFileDecryptor` KDoc: RSA-OAEP uses SHA-256 with MGF1-SHA1 (it said MGF1-SHA256; the algorithm is unchanged).
- **Managed trust roots.** A signed config may carry `trustRoots` (SPKI pins of root CAs). With `PinVaultConfig.Builder.managedTrustRoots()`, a host that has no pin entry is accepted when the platform's CAs validate its chain to a listed root and the leaf names the host; hosts with a pin entry are unchanged, and the feature is off by default. The list is stored with the config, validated like pins (at most 64, no duplicates) and part of change detection; a refusal is the new `ManagedTrustRootException`, which the recovery interceptor treats like an unknown host (one refetch per window). This is the device trust store with the authority taken away from it: a CA added to the device does not count, and a root the operator stops listing stops being trusted on the next config.
- **Where a key lives is reported, and can be required.** The library asks the Keystore for StrongBox first and the TEE next; what it got was never read back, so a ROM that made the key in software left the app (and the server) believing it was in hardware. Every key the library generates or imports is now inspected (`KeyInfo`) and its level logged; the new `KeySecurityLevel` (`strongbox` / `tee` / `software` / `unknown`) is on `ClientCertEnrollmentResult.Enrolled.keySecurityLevel`, in `PinVault.identityKeySecurityLevel()` and in the attestation report. `PinVaultConfig.Builder.requireHardwareBackedKeys()` refuses a `software` / `unknown` key: it is deleted again and the operation fails with the new `HardwareBackedKeyRequiredException` (enrollment, vault file keys, imported P12 keys, the user-auth key, and the store keys made on first use — `init` then returns `Failed`). Keys that already exist are used as they are.
- **An issuer pin checks the host name too.** A pin on a CA certificate says "a certificate this CA issued" — for a public intermediate, any site's certificate. The leaf must now also be issued for the host being connected to (a matching `subjectAltName`, the same rules as OkHttp's verifier), checked by the library itself at the handshake and on every request, so an app that passed its own builder with a relaxed `HostnameVerifier` to `applyTo` is covered. A leaf pin needs no name: the pinned key is the identity, so self-signed and SAN-less certificates work as before. The refusal is the new `HostnameMismatchException` (a `CertificateException`), which the recovery interceptor does not refetch for.
- **Pinned clients follow no redirect into the clear.** A client the library builds (`getClient()`, `getClient(settings)`) no longer follows an https→http redirect; the Config API's own client follows no redirect at all — not to another https host either, since a redirect carries the device headers and a 307 the enrollment body. Builders passed to `applyTo` keep their own settings.
- **Two pins must be two different pins.** A host entry listing the same hash twice passed the "primary + backup" rule and left a rotation nothing to fall back on; it is now refused like a malformed pin (`InvalidPinFormatException`). Bootstrap pins and `HostPin` constructed directly are not checked.
- **Consumer R8 rules no longer keep the library's class names.** The `-keepnames class io.github.umutcansu.pinvault.**` rule (there for readable Timber tags) published, in every consumer's release APK, the names of the two methods a hooking script needs to disable pinning. Minified apps now see obfuscated tags from PinVault; keep the names yourself if you need them in logs.
- **Attestation (Approov-style), see `ATTESTATION.md`.** `ConfigApiBlock.Builder.attestation()` (off by default), `attestationInterval(amount, unit)` (default 5 min, at least 1; a ceiling — the server's `nextAttestIn` and the token's expiry can make it sooner) and `tokenHosts(vararg patterns)` (pin host syntax; default: every host pinned by the block's live config plus its Config API listener). At `init` — after the stored config is loaded and the mTLS renewal check ran — and on every periodic update, each attesting block gets a nonce from `GET api/v1/attest/challenge`, builds the integrity report (`integrity.DeviceIntegrityProbe`: `app`, `device`, and the signals `rooted`, `emulator`, `debugger`, `debuggable`, `hooking_framework`, `app_integrity`, `cloner`, `unknown_installer`, `adb_enabled`, `software_key`, `key_unattested`, `old_patch_level`; a probe that fails contributes `error:<probe>` evidence, never a crash), signs `pinvault-attest:v1:<nonce>:<deviceId>:<sha256-hex(report)>` with the block's device key (made with the identity attestation challenge if it does not exist yet; the attestation chain goes with the first request and again when the server asks for it) and posts to `api/v1/attest` with `currentConfigVersion`, `currentIssuedAt` and the block's `wantPinsFor` as `hosts`. A pass holds the `PinVault-Token` in memory and applies an embedded signed config through the new `SSLCertificateUpdater.applySigned` (the fetched config's checks — signatures, scope, freshness, replay, plausibility — minus the fetch; unsigned blocks ignore it); a reject holds no token and gets no config; **`init` never fails on a verdict**. A coroutine per block re-attests at `min(nextAttestIn, interval, tokenExpiry − 60 s)` ±10 % while the process lives; failures back off 30 s → 5 min and keep the last token until it expires. Nothing new is written to disk.
- **The token header.** Every client the library builds or configures (`getClient()`, `getClient(settings)`, `applyTo`) carries an application interceptor (outside the recovery interceptor) that adds `PinVault-Token` to requests for a token host; without a valid token it attests once, synchronously, and sends the request bare when that fails. A `401` whose `WWW-Authenticate` names `PinVault-Token` or whose body says `invalid_token` forces one re-attestation and one retry, never for a one-shot request body; a rejected or failing device re-attests on its schedule, not per request. New public API: `PinVault.attestNow(configApiId?)` and `fetchAttestationToken(host?)` (suspend and callback), `attestationStatus(configApiId?)` → `AttestationStatus(result: PASS | REJECT | FAILED | NOT_ATTESTED | UNSUPPORTED, arc, rejectionReasons, warnings, tokenExpiresAt, lastAttestedAt, nextAttestAt, clockSkewMs, lastError, policyVersion)`, `attestationHeaderName()`, `AttestationTokenResult` (`Token | Rejected | Failed | Unsupported`), the event `PinVaultConnectionEvent.Attestation` (**an exhaustive `when` over the events needs a branch**), `PinVaultConfig.Builder.integrityVerdictProvider(provider)` with the SPI `integrity.IntegrityVerdictProvider` / `IntegrityVerdict` (Play Integrity's token travels verbatim as `verdictProvider`), and `expectedSignerSha256(vararg hex)` (the device raises `app_integrity` itself when none of the APK's signers matches). A block with a custom `CertificateConfigApi` reports `UNSUPPORTED`. The library manifest gains a `<queries>` list of root-manager packages so the `rooted` probe can see them on Android 11+. `PinVaultConfig` (`integrityVerdictProvider`, `expectedSignerSha256`) and `ConfigApiBlock` (`attestationEnabled`, `attestationIntervalMs`, `tokenHosts`) gained trailing constructor parameters with defaults.

### Server

- **Attestation** ([ATTESTATION.md](ATTESTATION.md)): the Approov-style layer that decides which app instances get pins and a token. `GET /api/v1/attest/challenge` hands out a stateless nonce (`base64url(ts ‖ rand ‖ HMAC[0..16))`, `ATTESTATION_NONCE_TTL_SECONDS`, default 120 s, single use through a bounded replay cache; `serverTime` for the clock check); `POST /api/v1/attest` checks, in order, the body shape (`400 unsupported_version` / `invalid_json` / `report_too_large`, 16 KB), the nonce (`400 nonce_invalid|nonce_expired|nonce_replayed`), the `SHA256withECDSA` signature over `pinvault-attest:v1:<nonce>:<deviceId>:<sha256-hex(report)>` with the device's EC P-256 key (`401 signature_invalid`), revocation (`403 device_revoked`), the registered key (`403 key_mismatch`; migration V21 `attested_devices`) and, on a first registration, the Android Key Attestation of the key under **`ATTESTATION_KEY_POLICY=off|warn|enforce`** (default `warn`; `enforce`: `403 attestation_required` / `attestation_invalid` + `reason`, no start without `ATTESTATION_PACKAGE_NAMES` + `ATTESTATION_SIGNER_SHA256`; the identity challenge `SHA-256("pinvault-identity-key:v1:" + deviceId)`, as for CSR enrollment). Both endpoints are on the public allowlist, counted by the refusal limiter, capped at the 64 KB device body limit and rate-limited (`ATTESTATION_RATE_LIMIT` 60 / address, `ATTESTATION_DEVICE_RATE_LIMIT` 30 / device per 10 min; the challenge at twice the address quota). `ATTESTATION_ENABLED=false` leaves them unmounted.
- **Policy evaluation and verdicts.** Every flag the report can raise (`rooted`, `emulator`, `debugger`, `debuggable`, `hooking_framework`, `app_integrity`, `cloner`, `unknown_installer`, `adb_enabled`, `software_key`, `key_unattested`, `old_patch_level`) is `reject`, `warn` or `ignore` per Config API (`attestation_policies`, `GET`/`PUT /api/v1/config-apis/{id}/attestation/policy`, version bumped on every change; `ATTESTATION_POLICY_DEFAULT=strict|lenient` for a scope without one, `ATTESTATION_TOKEN_TTL_SECONDS`, `ATTESTATION_INTERVAL_SECONDS`, `ATTESTATION_REVEAL_REASONS` its defaults). The server adds the signals a client cannot forge before evaluating: `app_integrity` from the report's package and signer digests against `ATTESTATION_PACKAGE_NAMES` / `ATTESTATION_SIGNER_SHA256`, `key_unattested` and `software_key` from the device record (a hardware-attested key clears both), `old_patch_level` from `device.securityPatch` against `ATTESTATION_MIN_PATCH_LEVEL`. Per-device `forceFail` (reject, reason `force_fail`) and `forcePass` (every raised flag demoted to a warning) come first. The answer carries `result`, the 8-hex `arc` (`HMAC(nonceKey, sorted reasons ‖ "|" ‖ sorted warnings)`, resolvable in the dashboard from the device's stored verdict), `warnings`, `rejectionReasons` only with `revealReasons`, `tokenTtlSeconds`, `nextAttestIn`, `device {registered, firstSeen, keyAttestation}`, `policyVersion` and, on a pass, `token`, `tokenExpiresAt` and — when the device's `currentConfigVersion` differs, it sent none, or its envelope is past half the config TTL — `config`: the same signed envelope `GET /api/v1/certificate-config` serves, scoped by the body's `hosts` and the device's host ACL (the GET's scoping and signing loop moved into shared helpers, `servedPinConfig` / `signEnvelope`). A rejected device gets no token and no config; a signer failure leaves the config out and keeps the verdict. The last report (app, device and signals blocks) and verdict are stored per device; hourly counters (`attestation_verdict_counts`, 30 days) feed `GET …/attestation/stats` (24 h / 7 d: passes, rejects, by reason, by warning, device counts).
- **`PinVault-Token`** (`service/attestation/PinVaultToken.kt`, no JWT library): HS256 JWT with `kid`, `iss pinvault`, `sub`/`did` = device id, `aud` = Config API id, `iat`, `exp`, `jti`, `arc`, `pol` and `anno` (the device's annotations, only when it has any). Secrets are 32 random bytes in `attestation_token_secrets`, encrypted under `VAULT_AT_REST_PASSWORD`, one active (made on first use, kid `YYYY-MM-DD-NN`), the previous ones kept for verification: `GET /api/v1/attestation/token-secrets` (requester-run under two-person approval, `attestation_token_secrets`), `POST …/rotate` (`attestation_token_secret_rotate`; answers the kid only), `DELETE …/{kid}` (`attestation_token_secret_delete`; the active one is `409 secret_active`). The reference verifier is the **`PinVaultTokenAuth`** plugin (`plugin/PinVaultTokenAuth.kt`: `kid` lookup, signature, `exp` with 60 s leeway, optional `aud` and required annotations; `401` with `WWW-Authenticate: PinVault-Token error="invalid_token", error_description="…"` and `{"error":"invalid_token","reason":"missing|malformed|unknown_kid|signature|expired|audience|annotations"}`); **`MOCK_HOST_REQUIRE_TOKEN=true`** installs it on every mock TLS/mTLS host. `SERVER_IMPLEMENTATION_GUIDE.md` has verification snippets for Kotlin/Java, Node and Python.
- **Attestation admin API** (management port; Config API ports with `CONFIG_API_ADMIN_ROUTES=on`): `GET …/attestation/devices?result=&q=&page=&pageSize=` (last verdict, ARC, reasons, warnings, key attestation, overrides, key mismatches), `GET …/devices/{deviceId}` (with the trimmed last report), `PUT …/devices/{deviceId}` `{forcePass, forceFail, annotations}` (gated `attestation_device`; a device may be annotated before it ever attested), `DELETE …/devices/{deviceId}` (forgets the key so a reinstalled app registers again; gated `attestation_device`), `GET …/stats`. New audit actions: `attestation_policy_updated`, `attestation_device_annotated`, `attestation_device_forgotten`, `attestation_device_registered`, `attestation_key_mismatch` (one entry a minute per device), `attestation_rejected` (routine — not in `*` webhooks; written when a device's verdict changes, the repeats summarised per minute), `attestation_token_secret_rotated`, `attestation_token_secret_deleted`. Deleting a Config API purges its attestation tables; `GateCoverageTest` covers the new writes.
- **`CONFIG_API_ADMIN_ROUTES=off`**: the Config API listeners answer device endpoints only; every admin route is `403 admin_routes_disabled` there, key or no key (refused before the key is looked at, so the device ports give no oracle on keys). Administration happens on the management port alone, and a leaked `API_KEY` cannot write pins from the internet-facing ports. Default `on` keeps the demo flows; the production profile sets and enforces `off`.
- **Managed trust roots** ([ATTESTATION.md §10](ATTESTATION.md)): the pin config carries an optional `trustRoots` list (SHA-256 SPKI pins of root CAs; migration V22 `pin_config.trust_roots`), validated like pins (format, no duplicates, at most 64), part of the signed payload and left out when empty so older clients see nothing new. `PUT /api/v1/certificate-config` replaces the list when the body carries the field and keeps it when the body does not (an older script editing pins cannot drop the roots); a change writes a `trust_roots_updated` history entry (host `*`) and audit action. The dashboard edits the list on each Config API's General tab, and `GET /api/v1/all-configs` reports it.
- **`HOST_CLIENT_CERT_REQUIRE_GRANT=true`**: a host's client certificate (one private key the whole fleet shares) is handed only to devices the device host ACL names; a scope without any ACL serves it to nobody (`403 host_not_allowed`). Unset keeps the open behaviour, where any enrolled device — one that came in with a shared enrollment code, or a phone compromised before its revocation — could collect every host's key. The production profile sets and enforces it.
- **`VAULT_DOWNLOAD_CONCURRENCY_TOTAL`** (default 16): vault downloads served at once in total, on top of the per-address cap. Each download holds the whole file, and for `end_to_end` / `user_auth` its encrypted copy, in memory; a 50 MB `public` file fetched from a handful of addresses at once could exhaust the heap. The Docker images start the JVM with `-XX:MaxRAMPercentage=60`.

- **The two-person rule could be bypassed with an encoded slash.** `POST /api/v1/config/x%2Fy/update?configApiId=default-tls` reached the handler with the query's scope (Ktor lets a query parameter shadow a path parameter in `call.parameters`), while the approval gate decoded `%2F` into a separator and matched no rule, so one admin key changed signed pins with no second admin; `fetch-cert-url`, `force-update` and `clear-force` had the same hole. Every listener (management, Config API, recovery) now refuses `%2F`, `%5C`, `%2E`, `%25` and backslashes in the path with 400 (`EncodedPathGuard`), every handler reads path values with `call.pathParameters`, `canonicalPath` keeps an encoded slash inside its segment, and the approval summary names the scope and host the handler changes.
- **Stored HTML in the dashboard's vault tab.** Upload `?policy=` / `?encryption=` were stored unvalidated and rendered unescaped, so an admin could plant an invisible full-page button that approved their own pending change when another admin clicked anywhere. The upload route validates policy, encryption and key (400 otherwise); an unknown stored encryption is no longer served as plaintext (500); the vault, host and section tabs escape every interpolated value; approve and reject ask for confirmation with the change summary; the CSP adds `form-action 'none'; base-uri 'none'`.
- **Open enrollment could take over an enrolled identity.** With `ENROLLMENT_MODE=open`, enrolling with another device's id and no `deviceUid` replaced its key. Now `409 identity_already_enrolled` unless the same key asks again, `deviceUid` is always the device id, and the P12 path is refused (`403 csr_required`). A token re-enrollment over a new key retires the old key at once; a policy pickup cannot replace an identity enrolled under its id in the meantime.
- **Revocation reaches the vault and every client-CA listener.** Revoke and forget also revoke the device's vault tokens in every scope and delete its E2E and user-auth keys (one transaction; see the proof rule below); the mock mTLS hosts run `RevocationGate`; a revoked device's `X-Device-Id` is refused on token, end_to_end and user_auth downloads and on key registration (`403 reenroll_required`).
- **Vault encryption `user_auth`** (migration V16 `device_user_auth_keys`): the file is sealed per download to the device's user-auth key, registered with `POST …/vault/devices/{deviceId}/public-key` and `"purpose":"user_auth"` (kept apart from the E2E key); without one, `412 user_auth_key_required`.
- **Android Key Attestation for user-auth keys** (`USER_AUTH_ATTESTATION=off|warn|enforce`, default `warn`). The registration body takes `"attestationChain": [base64 DER, leaf first]`; the challenge is SHA-256 of `"pinvault-user-auth-key:v1:" + deviceId`. The chain must verify to a Google hardware attestation root (`attestation/google-hardware-attestation-roots.pem`, trusted by key; leaf and intermediates must be current; `ATTESTATION_REVOKED_SERIALS_FILE` for Google's status list, read from disk), the leaf must be the registered key, and its KeyDescription (v3–v400) must show TEE/StrongBox, user authentication required with no hardware `authTimeout` over 10 s (`auth_timeout_too_long`), purpose DECRYPT, origin GENERATED, a locked bootloader with Verified boot (`ATTESTATION_REQUIRE_VERIFIED_BOOT`, default on), and a package in `ATTESTATION_PACKAGE_NAMES` and a signer in `ATTESTATION_SIGNER_SHA256`. Cheap checks (chain length and size, decoding, the leaf's key, the last certificate against the roots by key or issuer name) run before any signature; a caller without a credential is counted against `DEVICE_KEY_RATE_LIMIT` before its chain is verified. **An attestation counts only with the app binding** (both `ATTESTATION_PACKAGE_NAMES` and `ATTESTATION_SIGNER_SHA256`; otherwise any app can attest a key for any device id): `enforce` refuses to start without both, `warn` warns at start-up and stores a passing chain as `app_binding_not_configured`. **Replacing a registered user-auth key needs, in every mode, both the device's credential (a bound client certificate or the device's `end_to_end` / `user_auth` file token) and a passing attestation** — root running as the app has the first, a stranger with a phone of their own the second: otherwise `409 user_auth_key_exists` with `reason` `credential_required` (the chain is then not verified), `attestation_off` or the attestation's reason; `off` never replaces. An admin reset (`DELETE …/public-key?purpose=user_auth`) makes the next registration a first one. First keys: `enforce` needs a passing chain (`403 attestation_required` / `403 attestation_invalid` + `reason`); `warn` and `off` accept one without a credential (trust on first use), `warn` storing the outcome (migration V17: `attested`, `attestation_security_level`, `attestation_reason`), listed by the new `GET /api/v1/config-apis/{configApiId}/vault/devices/user-auth-keys`. Registrations, replacements (webhook) and refusals are audited with the outcome. SECURE_OPERATIONS has the runbook for the by-design lockout (a retired key that cannot be replaced waits for an admin reset). The E2E key is unchanged.
- **Revocation cuts off only the devices an identity proved.** Revoke/forget used to wipe the vault tokens and keys of — and block — every `deviceUid` the identity sent at enrollment, so enrolling with a victim's device id and getting revoked took the victim down. Now: the client id itself and the device ids for which it used one of the device's vault tokens over its own certificate (a download, or a key registration carrying the token), or re-registered over it the key the device had on file before the identity was enrolled (V17 `identity_devices`). Registering a new key — or its own key again — over a certificate proves nothing: the certificate is tied to the device id only by the enrollment claim. Claimed-only ids come back as `unverifiedDeviceIds`; `?cascadeUnverified=true` on `DELETE /api/v1/client-certs/{id}` or `…/forget` cuts them off deliberately. The dashboard shows them after *Revoke* (with "Cut these devices off too") and before *Forget identity* (new read-only `GET /api/v1/client-certs/{id}/devices`; "Forget only" / "Forget and cut these devices off"), each cascade behind a confirmation, never by default.
- **No revocation oracle.** `403 reenroll_required` on vault downloads and key registration comes only after the caller authenticated with the device's credential (valid token or bound certificate; an attestation is not one). Others are handled exactly as for any device id, on every request of a sequence: a key registration without a credential keeps the first key and answers a different one with `409`, and an `end_to_end` / `user_auth` file under a policy that authenticates nobody is answered by whether a key is on file (`412` when not). The earlier form — answer 200 and store nothing — still told revoked ids apart: a second, different key got 200 instead of 409, and a `public` end_to_end file 412 instead of the file. Revocation still deletes the device's keys and tokens and refuses its certificate and tokens; a key registered afterwards without a credential opens only `public` files, which a made-up device id opens too.
- **Unauthenticated CPU and memory exhaustion on the device endpoints.** (1) A vault download decrypted the file — 200 000 PBKDF2 rounds — before looking at the access policy, and the key-replacement proof did the same for any `X-Vault-Key`: now existence, policy, token, `304` and the device-key lookup are decided from metadata, the file is opened only for a request that is answered with it, and the at-rest key is derived once per process (one salt per process for writes, a bounded cache for older blobs; blob format, `VAULT_AT_REST_PASSWORD_PREVIOUS` rotation unchanged). (2) The 64 KB body cap looked only at `Content-Length` / `Transfer-Encoding`, which HTTP/2 needs neither of: it is now enforced while reading on every device route (`413`), and vault uploads are capped at `VAULT_MAX_FILE_BYTES` (default 50 MB). (3) A CSR's signature was verified before its key was looked at: now at most 8 KB, RSA 2048–4096 with e = 65537 or EC P-256/P-384 (named curves), checked first (`400 invalid_csr`; no malformed request ends in a 500); renewal and policy pickup look up the identity / request and compare the key before verifying a signature. (4) Limits are per source address (IPv6 by /64), never per caller-chosen id: `DEVICE_REFUSAL_RATE_LIMIT` (default 300 refusals per 10 minutes on enrollment, key registration and downloads, then `429` before anything is read; served requests are not counted), renewal refusals per address plus successful renewals per identity, and a full limiter refuses new keys instead of dropping a live window.
- **Device reports are validated and cannot erase history.** `POST /api/v1/vault/report` and the two connection-history reports stored whatever they were sent into tables trimmed table-wide (500 / 200 rows), so a few hundred made-up reports wiped every Config API's history and pushed real `pin_mismatch` rows out. Now: key, ids, status and `authMethod` are checked (`400`), free text is cut to a printable line, the time is the server's, `REPORT_RATE_LIMIT` (600) per address and `REPORT_DEVICE_RATE_LIMIT` (120) per device per 10 minutes, on mTLS a device reports for itself only (`403 device_identity_mismatch`), and rows are trimmed per Config API with failures under their own, larger quota.
- **Enrollment is not served over plain HTTP.** The management port's copy of `POST /api/v1/client-certs/enroll` answered on the cleartext connector — token in, private key and its password out. Device endpoints that take a token or return a key now answer `403 tls_required` there unless the connection is from the server's own machine (`CleartextGuard`); use a Config API port or `MANAGEMENT_HTTPS_PORT`.
- **Host client certificates honour the device host ACL.** `GET /api/v1/client-certs/{hostname}/download` gave any enrolled device every host's client key in the scope; where the Config API has an ACL the host must be allowed for the certificate's device (`403 host_not_allowed`).
- **mTLS listener restarts are coalesced.** Each server-made P12 enrollment restarted every mTLS listener inside the request; restarts now run at most once per `MTLS_RESTART_MIN_INTERVAL_SECONDS` (default 5), later requests folded into one.
- **Enrollment cannot undo a revocation.** The CSR paths write `client_identities` and `client_certs` in one transaction, and every enrollment's `client_certs` write is an upsert that never touches a revoked row (it used to be `INSERT OR REPLACE … revoked = 0` after the identity commit).
- **A vault file's encryption or access-policy change bumps its version**, so devices holding the old form (a plain copy of a file now sealed) fetch it again instead of getting `304`.
- **Two-person approval now covers trust material, enrollment and the vault.** With `PIN_CHANGE_APPROVALS=2` one admin could still upload any certificate — a CA included — into the mTLS truststore, generate a client P12 (un-revoking its id on the way), create enrollment codes, switch code-less applications on, mint enrollment and vault tokens, replace a signed vault file, turn a `token_mtls` file `public` or reset a device key. Gated now, each under its own operation: `client_cert_upload`, `client_cert_generate`, `enrollment_policy_create`, `enrollment_open`, `enrollment_token`, `vault_upload`, `vault_delete`, `vault_policy`, `vault_token_issue`, `vault_token_revoke`, `device_key_reset`, `vault_enabled`. Still at once, on purpose: revocation and forget, stopping a code, turning code-less applications off (new `DELETE /api/v1/enrollment-open`), and deciding on a device that asked to enroll. `APPROVAL_EXEMPT_OPERATIONS` (comma-separated operation names, empty by default, unknown name = startup error) takes operations out of the rule. Operations whose answer carries a secret (P12, enrollment token or code, vault token) are not replayed: the request becomes `approved` (new status, `?status=open` lists pending and approved) and its requester sends it again to run it once; the secret is never stored or shown to the approver (migration V18).
- **Client certificates:** an upload must be one end-entity certificate — a CA or `keyCertSign` certificate, one without the clientAuth usage, an expired one are `400 invalid_client_certificate`; ids must match `[A-Za-z0-9._:-]{1,64}`; generate and upload use the unless-revoked upsert and answer `409 revoked` for a revoked id; an upload restarts the mTLS listeners (coalesced; a generated P12 needs no restart since it comes from the client CA, see below) and both are audited (`client_cert_uploaded`, `client_cert_generated`).
- **Vault administration left the device-facing ports.** `/api/v1/vault/…` on a Config API listener serves the download, the report and device-key registration only; upload, delete, policy, tokens, distributions, stats and the key reset are served only under `/api/v1/config-apis/{configApiId}/vault/…` on the management listener (scripts using the old paths must move). A token of another Config API can no longer be revoked through a scope's path (`404`). A missing file answers `404` only to a caller with an admin key or a client certificate; anyone else gets the `401` a token file gives, so file names cannot be enumerated (an `api_key` file still answers with its own text).
- **A certificate change is planned when requested and applied as approved.** The approval card said `fetch-cert-url (every Config API that pins it)` and the URL was fetched — or the key generated — at approval time. Now host and bootstrap certificate changes (generate, regenerate, rotate-to-backup, upload, fetch) are worked out at request time: pins, subject, validity and the Config APIs that change are stored with the request, shown on the card and in the approve confirmation, and exactly that plan is installed (no second fetch; a replay without its plan is refused; a scope whose pins changed meanwhile makes the request stale). The summary is built from what the handler reads, so an ignored body field cannot appear in it. `PIN_LIVE_CHECK` now also runs on every certificate change of a host and every add-host route, with the same `422` / `liveCheckOverride` / audit handling as a pin update; with approvals a failing check is refused when the change is requested.
- **Admin API vs. the browser.** State-changing admin requests are refused when `Origin` is not the server's own or `Sec-Fetch-Site` is `cross-site`/`same-site` (`403`; `ADMIN_ALLOWED_ORIGINS` for a proxy), and must be `application/json` or carry `X-API-Key` / `X-PinVault-Admin` (`415`). With `ALLOW_ANONYMOUS_ADMIN=true` the management listener binds `127.0.0.1` (new `MANAGEMENT_BIND`) and every admin request must be addressed to localhost with the listener's port (`403 host_not_allowed`; `MANAGEMENT_ALLOWED_HOSTS`), which stops DNS rebinding. The dashboard keeps the admin key in sessionStorage (a localStorage copy is moved once and deleted) and marks its requests. Unhandled errors on the management listener answer `500` with an `errorId` instead of the exception text.
- **External signers are not run per request.** With `CONFIG_SIGNERS=command|pkcs11` the signature cache is always on and serves every client: one signing per distinct config or vault file version, at most `SIGNER_MAX_CONCURRENT` (2) at once with `SIGNER_MAX_QUEUE` (8) waiting, `503` beyond. A signer command gets an environment allowlist (`PATH`, `HOME`, `LANG`, `TZ`, `SIGNER_*`, plus `SIGNER_PASS_ENV`) instead of the server's environment minus a denylist that missed `*_PREVIOUS`, `CLIENT_P12_PASSWORD`, `NOTIFY_WEBHOOK_*` and `ADMIN_KEYS`.
- **Audit:** server-made P12s are recorded as `client_cert_issued` (`format`), and enrollment tokens, vault uploads/deletes/policy changes/tokens, the vault switch, host ACL changes, bootstrap certificate changes and admin downloads of a host's client key have their own actions (all sent to the webhook). Refused enrollments and refused cross-site admin requests are summarised (one entry a minute) instead of written per request. **Webhook signatures now cover `<timestamp>.<body>`** with the timestamp in `X-PinVault-Timestamp`: receivers that verify the signature must include it (and can now reject replays).
- **Deployment defaults.** The server refuses to start while `KEYSTORE_PASSWORD`, `VAULT_AT_REST_PASSWORD` or (with a local signer) `SIGNING_KEY_PASSWORD` is unset, unless `ALLOW_DEMO_SECRETS=true`. `demo-server/docker-compose.yml` publishes the management port on 127.0.0.1 and runs as uid 10001 (`Dockerfile` `USER`; `chown -R 10001:10001 data` once, or `PINVAULT_UID`). Certificate fetches refuse link-local and cloud-metadata targets always and loopback / private networks unless `FETCH_ALLOW_PRIVATE_TARGETS=true`, resolving the name once and connecting to the checked address. Admin uploads and JSON bodies are capped at `ADMIN_UPLOAD_MAX_BYTES` (1 MB).
- **Approval:** host ACL writes (`PUT …/default-host-acl`, `PUT …/devices/{deviceId}/host-acl`) are gated (operation `host_acl`). Summaries are one line — control characters, line separators and bidi overrides become spaces — and capped (300; body fields 120), so a body field cannot draw a fake line in the approver's confirm. Bare `http` audit entries take `configApiId` from the path when the route has one.
- Sample host: `offline-keys/` in `.dockerignore`; the production profile sets `USER_AUTH_ATTESTATION=enforce` and `ATTESTATION_PACKAGE_NAMES=com.example.sampleclient` and requires `ATTESTATION_SIGNER_SHA256` (`setup.sh --production` asks for it or takes `--attestation-signer`, and stops without it; demo stays `warn` with both empty); `client-config.sh` writes `target.requireCaTrust=false` only when openssl reports a real chain fault for the target, not when the local openssl has no CA store.
- **A P12 holder could act as another device.** Server-made P12s were self-signed leaves without basicConstraints, each added to the mTLS truststore as its own anchor, and the identity is the certificate's CN: an anchor that may sign (a v1 certificate on any JDK, any of them with `jdk.security.allowNonCaAnchor=true`) let its holder sign a leaf naming another client id and be accepted as that device. P12s now come from the client CA (CA:false, clientAuth, chain leaf + CA; nothing is added to the truststore, no listener restart). Every mTLS request (`RevocationGate`, Config APIs and mock hosts) must present the certificate on record for the id its CN names — one over the identity's key for CSR identities, exactly the stored certificate for P12 and uploaded ones — or gets `403 reenroll_required`. Existing self-signed anchors keep working until they expire or the id enrolls again (CSR, P12 or *Generate*), which removes the anchor, retires its key and restarts the listeners once; server-made keys are recorded in `client_keys` so a later enrollment or a forget retires them. Uploads must be v3 leaves whose extended key usage includes clientAuth (v1 certificates and certificates without the extension are now `400`).
- **`ENROLLMENT_P12=on|off`** (default `on`; production `off`): off — and under `ENROLLMENT_ATTESTATION=enforce` — every path that would make a key on the server (both copies of `POST /api/v1/client-certs/enroll`, `POST /api/v1/client-certs/generate`) answers `403 csr_required` before anything is spent.
- **Android Key Attestation of enrollment keys** (`ENROLLMENT_ATTESTATION=off|warn|enforce`, default `warn`). Every CSR path (token, enrollment code submit and pickup, code-less application, open mode) reads `attestationChain` and checks it as an identity key: leaf = the CSR's key, challenge SHA-256(`"pinvault-identity-key:v1:" + deviceUid`, or `deviceId` without one), purpose SIGN, origin GENERATED, TEE/StrongBox, verified boot, the app's package and signer — after the cheap refusals and before a token, slot or request is spent. `enforce`: `403 attestation_required` / `attestation_invalid` + `reason`, and no start without the app binding; `warn`: the verdict is stored (migration V19: `attested`, `attestation_security_level`, `attestation_reason` on `client_identities` and `enrollment_requests`) and shown next to each waiting request and in the client certificate list (*Hardware-attested* / *Not attested* / *Not checked* / *Made by the server*), and in the audit entries. A request recorded under `warn` is issued under `enforce` only with a passing chain at pickup.
- **User-auth keys against root running as the app.** Root can delete the per-use key and register a time-bound one it made in the app's uid with the right challenge; `authTimeout` ≤ 10 s used to pass on every Android version. Now `authTimeout`, `noAuthRequired` and the new `allowWhileOnBody` check are read from both authorization lists, a key whose osVersion is Android 11+ with any `authTimeout` > 0 is `time_bound_key`, and `USER_AUTH_REQUIRE_PER_USE=true` (default false; production true) refuses every time-bound key. The kind is stored with the key (V19 `key_kind`, `auth_timeout_seconds`, `biometric_only`) and listed. Under `enforce` a key on file without a passing attestation is not sealed for (`412 user_auth_key_required`, `reason: key_not_attested`; with per-use only also `time_bound_key` / `key_kind_unknown`), and the same key sent again without a passing chain is `403`. Optional `ATTESTATION_MIN_PATCH_LEVEL` (YYYYMM, osPatchLevel) refuses older phones (`patch_level_too_old`), for both key kinds.
- **The attestation revocation list is re-read.** `ATTESTATION_REVOKED_SERIALS_FILE` is read again when its modification time changes (checked every 10 minutes and on verifications; a broken file keeps the last good list); `ATTESTATION_STATUS_MAX_AGE_HOURS` (default off) lets no attestation pass once the file is older (`revocation_list_stale`). The server still never goes to the network: `demo-server/scripts/fetch-attestation-status.sh` (curl, content check, atomic rename) is the cron job.
- **Verification code: 80 bits.** The code next to a waiting request is the first 10 bytes of SHA-256(SPKI), `XXXX-XXXX-XXXX-XXXX` (vector SHA-256("pinvault") → `0XMH-GCGP-BW6Z-10F6`), as the library shows it; 40 bits could be matched by generating keys. A device with duplicate requests: reject them all and let it apply again (dashboard and SECURE_OPERATIONS).
- **Signatures name their Config API.** Every signed config payload carries `"configApiId": "<scope>"` (absent from unsigned answers); vault downloads also send `X-Vault-Signature-V2` / `X-Vault-Signatures-V2` over `pinvault-vault-file:v2:<configApiId>:<key>:<version>:<sha256>` (v1 headers kept). The vault signature cache is keyed by scope and holds both schemes. Signing-key sets are unchanged (signed offline; the library reads no scope from them).

- **Host names are checked when they are added**, with the rules the library applies (`service/HostPatternRules.kt`: LDH labels, one leading `*.`, no `*.com`, optional `:port`): `PUT /certificate-config`, the host-adding certificate routes and their approval plans answer `400`. A config with such an entry used to be published and then refused as a whole by every device.
- **Refused token enrollments are audited per client id.** With a valid token, the first refusal of a minute for each client id is written on its own (`client_cert_enroll_refused`, target = client id, e.g. "device … is enrolled as …"); further ones and every unauthenticated refusal are counted into the summary of the minute.

- **Security review 2026-10-05, admin side.** (1) Without admin keys (`ALLOW_ANONYMOUS_ADMIN=true`) the Config API listeners — every interface — accepted every admin route, `PUT /api/v1/certificate-config` included, from the LAN: they now serve device endpoints only (`403 admin_key_required`), and the management listener answers anonymous admin only to a loopback peer or `ANONYMOUS_ADMIN_PEERS` (IPs/CIDRs, e.g. a container gateway; `403 peer_not_allowed`) — the `Host` header alone let any program claim `localhost`. (3) Pin writes apply the library's rules — hosts unique ignoring case, ≤ 2000 hosts, 2–32 pins per host, each 43 Base64 characters + `=` (`service/PinConfigRules`, next to `HostPatternRules`): the editor, adding a host (`checkNew`), certificate plans, propagation and the approval description. (4) With `PIN_CHANGE_APPROVALS` ≥ 2, approving an enrollment request needs a personal key that did not create the code (`409 named_admin_required` / `own_enrollment_code`; code-less: any personal key, recorded as `approvedBy`). (6) `ADMIN_AUTH_FAILURE_LIMIT` (30 invalid keys per address per 10 minutes, `0` = off) → `429`. (7) Config API start/stop validate `id` and `mode`, answer built JSON, and the approval card names the mode and the API a start would stop (routes moved to `route/ConfigApiAdminRoutes.kt`). (8) A host client P12 must hold exactly one private key; that entry is described, recorded and stored. (9) Change-request bodies and plans (uploaded P12s and passwords, generated keys) are stored under `VAULT_AT_REST_PASSWORD`. (10) `GateCoverageTest` walks the route tree: an admin write neither gated nor listed as deliberately ungated fails the build. (11) `API_KEY` must have 16 characters unless `ALLOW_DEMO_SECRETS=true`. (12) Issuing a client certificate puts the client CA back into a missing client truststore (an mTLS listener could not start until a restart).
- **Security review 2026-10-05, device side.** (1) **Proven device ids** (migration V20 `client_certs.device_uid_proven`, `enrollment_tokens.device_uid`): a `deviceUid` sent at enrollment is a claim; only a proven one — the client id itself, a token the admin bound to it (`POST /api/v1/enrollment-tokens/generate {"deviceUid":…}`, mismatch `403 device_uid_mismatch`), or a passing attestation with the app binding — lets a certificate replace the device's keys, open its `token_mtls` files, take host certificates under its ACL grants or lift its revocation block. Over mTLS a claimed binding replaces an E2E key only with the device's token, as on TLS; re-sending the registered public key is no proof any more. (2) Re-asks with the same key (open mode, enrollment codes, also after a code was stopped) get the certificate already issued while half its lifetime is left; `ISSUANCE_RATE_LIMIT`, `KEY_REPLACEMENT_RATE_LIMIT`, `PICKUP_RATE_LIMIT`, `PICKUP_SOURCE_RATE_LIMIT` bound the rest; the webhook queue keeps 100 places for security events. (3) Rate limiters no longer refuse every new key when full: source keys overflow into /24 (IPv4) or /48 (IPv6) buckets, identity keys fail open; renewal sources and identities have separate tables; `DeviceRefusalLimit` records when the quota is used up. (4) Vault reports on TLS are limited per address only; `client_devices` keeps `CLIENT_DEVICES_MAX` (20 000) rows. (5) Vault signatures are cached per file version always, and `VAULT_DOWNLOAD_CONCURRENCY` (4) downloads run at once per address. (6) Lapsed enrollment requests are expired at most every 30 s (an overdue one at once). (7) Open mode refuses a `deviceUid` other than the `deviceId` (`400 device_uid_mismatch`); attestation is checked against the stored device id. (8) One active identity per device id is decided in the write (`client_certs` upsert), legacy open-mode rows included. (9) A renewal CSR identical to the last accepted one is refused (V20 `last_renewal_csr_sha256`). The management-port enrollment copy logs refusals per client id and honours bound tokens; vault encryption errors answer an `errorId`; enforce without `ATTESTATION_REVOKED_SERIALS_FILE` warns at start-up.
- **Dashboard: bind an enrollment token to a phone.** The enrollment-token form has an optional *Device id (ANDROID_ID)* / *Cihaz kimliği (ANDROID_ID)* field, sent as `deviceUid`, with a short hint: filled in, only that phone can use the token and its files and keys can be bound to its certificate (the sample app shows the id on its mTLS screen). `GET /api/v1/enrollment-tokens` now returns `deviceUid` (null for an unbound token) and the token list shows it in a *Device* column ("any device" otherwise). `openapi.yaml` documents `deviceUid`, `expiresAt` and `expired` on `EnrollmentToken`.

## 2.1.1 — 2026-10-02 — Revocation and renewal reach every client

### Library

- **A revoked device hears it at its next request.** The server answers a revoked identity `403 reenroll_required` on every mTLS request, but only the renewal endpoint read that answer: a revoked device kept running on its stored config and files until its renewal came due (day 60 of 90). Every request of a Config API — config, scoped config, vault files, device key registration, reports, renewal — now emits `ClientCertRenewal(status = REENROLL_REQUIRED)`, once per certificate. `InitResult` is unchanged.
- **Clients built with `applyTo` follow renewal and re-enrollment.** `applyTo` captured the client certificate loaded when the client was built, so an app-built mTLS client (for example the one passed to `PinVaultBackendReporter`) kept presenting the superseded certificate after a renewal, and a revoked one after a re-enrollment, until the process restarted. Its socket factory now opens each connection from an SSLContext made for the identity loaded at that moment, replaced on every identity change; a fresh context also keeps a new connection from resuming a TLS session made with the old certificate. Open connections keep their certificate until they close: evict the pool after a re-enrollment.

### Demo app

- Logs the re-enroll event. Espresso `mtlsConfig_revoked_device_hears_it_at_next_start` revokes an enrolled device and checks that the next start reports it without a renewal request.

## 2.1.0 — 2026-10-02 — Device-held keys and certificate renewal

A device's mTLS certificate used to be a 365-day self-signed P12 the server generated; nothing renewed it, so an expired certificate locked the device out of the mTLS Config API for good. Enrollment now keeps the private key on the device and the certificate renews itself.

### Library

- **CSR enrollment is the default.** `enroll` / `autoEnroll` generate an EC P-256 signing key in the Android Keystore (`ClientIdentityKeyProvider`, one per `clientCertLabel`), send a PKCS#10 request over it with `X-PinVault-Features: csr`, and store the chain the server issues (`EnrollmentResult.certificateChainPem`). The key never leaves the device; it is generated with `DIGEST_NONE` as well as SHA-2, because Conscrypt signs the TLS handshake with a raw `NONEwithECDSA` operation on Keystore keys and silently presents no certificate otherwise. A server that ignores the feature answers with a P12 in the same request, which is stored exactly as before, so nothing changes against an older server or a custom backend. Stored credentials now take precedence over a `clientKeystore(...)` bundled in the app, which is the bootstrap identity for an mTLS Config API.
- **Automatic renewal.** At init and on every periodic update the library reads the stored certificate's dates (no network) and renews once less than a third of the lifetime is left (`clientCertRenewalThreshold`) over the block's own connection, or — expired, or refused by the server — over `renewalUrl(...)` (default: the block URL), where the CSR signature is the proof of identity. An issued chain is checked (valid now, over this device's key, signed by the issuer sent with it) before it replaces the old one. `PinVault.renewClientCertIfNeeded(configApiId, force)` → `ClientCertRenewalResult` (`Renewed(notAfter, via) | NotNeeded | ReenrollRequired | Failed | NotApplicable`), `PinVault.enrolledClientNotAfter(context)`, `disableClientCertRenewal()`.
- **Enroll before init.** `PinVault.enroll(context, config, token)`, `autoEnroll(context, config)` and `isEnrolled(context, config)` work without an initialized PinVault, so an app whose Config API is an mTLS listener starts with "enroll if needed, then one `init`". `init` no longer contacts a backend it cannot reach: a block with an `enrollmentUrl` and no client certificate returns at once with `InitResult.Failed(… ClientCertificateRequiredException)` — or `Ready` from a stored config — instead of retrying a refused handshake three times. (Device-identity lookup no longer depends on fields only `init` sets.) From Java the last one is `isEnrolledWithConfig(context, config)`: under the same name, every existing `isEnrolled(context, null)` call would no longer compile (found by the sample client; `JavaCallerCompatTest` keeps it so).
- **`enrollmentUrl(...)`** on a Config API block: where `enroll` / `autoEnroll` go. A device has no client certificate before it enrolls, so an mTLS Config API refuses the enrollment at the handshake; point this at the backend's TLS listener. Default: the block URL, as before. (The demo app's "Enroll" button on its mTLS screens failed for exactly this reason; it now enrolls over :8091.)
- **Pins per port.** A `HostPin("host:port", …)` entry applies to that listener only and, when present, is the only set used for it; the bare `host` entry keeps covering the host's other ports. Used to pin the recovery door to the backend's CA without widening what the Config API ports accept. (The `HostPin("host:8091", …)` examples in the `ConfigApiBlock` docs were never matched before — lookups ignored the port.)
- **A renewal must come from the current CA.** An issued chain whose leaf does not verify with the issuer of the certificate it replaces is refused, even if it arrives with a CA of its own.
- **`PinVaultConnectionEvent.ClientCertRenewal`** (status, expiry, door used). Adding a subclass to the sealed event class is a source-level change for consumers whose `when` over the event has no `else` branch — the class documentation always asked for one.
- **`CertificateConfigApi.enrollWithCsr` and `renewClientCert`**, both with default bodies (`null` / `Unsupported`), so Kotlin implementers need not change; Java implementers delegate to `CertificateConfigApi.DefaultImpls`.
- The Config API's pinned client is rebuilt after enroll, renew and unenroll, so a new identity is presented to the Config API at once instead of after a process restart.
- `unenroll` also deletes the device identity key; a re-enrollment is a new identity.
- **Why an enrollment failed.** `enrollForResult` and `autoEnrollForResult` (with and without a config) return a `ClientCertEnrollmentResult`: `Enrolled`, `Refused` with an `EnrollmentRefusal` (`INVALID_TOKEN`, `DEVICE_ALREADY_ENROLLED`, `REVOKED`, `TOKEN_REQUIRED`, `OTHER`) and the server's own words, or `Failed` when no usable answer came back. Before, a used token, a device enrolled under another id and a network error all looked like `false`, and apps told users their token was wrong. The `Boolean` `enroll` and `autoEnroll` are unchanged. `DefaultCertificateConfigApi` reads the reason from a 4xx answer and throws `EnrollmentRefusedException`; a custom `CertificateConfigApi` throws it to report a refusal.
- **Enrollment codes, and waiting for approval.** A code many devices share enrolls through the same `enroll` / `enrollForResult` as a one-time token. When its policy asks for approval the result is the new `ClientCertEnrollmentResult.Pending(requestId, clientId, message, retryAfterSeconds)` (`DefaultCertificateConfigApi` reads it from a `202`; a custom backend throws `EnrollmentPendingException`). The library keeps the key and the request id (per label, in the client-cert store) and asks again with a CSR from the same key: `PinVault.checkPendingEnrollment(context[, config])`, and on its own at `init` (before the first config fetch, so an approved device reaches an mTLS Config API at once) and on every periodic update. `PinVault.isEnrollmentPending(context[, config])` (Java: `isEnrollmentPendingWithConfig`). A rejected request — or one the server no longer knows — is forgotten together with its key, so the next attempt is a new request; `unenroll` gives a waiting one up. New refusals `EnrollmentRefusal.REJECTED` and `LIMIT_REACHED`. `enrollWithCsr` gained a `requestId` parameter (default `null`).
- **Applications without a code, and a verification code.** Against a server that takes applications without a code, `autoEnroll` / `autoEnrollForResult` returns `Pending` the way a code with approval does, and the device waits the same way. `Pending.verificationCode` (and `EnrollmentPendingException.verificationCode`) is a short code made from the device's own key — the first 40 bits of the SHA-256 of its public key in Crockford base32, `4F7K-2QXM` — which the dashboard shows next to the request, so the administrator can tell the device in front of them from a stranger; `PinVault.enrollmentVerificationCode(context[, label])` reads it while waiting. A request nobody answered in time is refused with the new `EnrollmentRefusal.EXPIRED` and forgotten with its key; when `enroll` / `autoEnroll` itself meets a lapsed or unknown request, it applies again at once over a new key.

### Demo server

- **A client CA** (`certs/client-ca.jks`, EC P-256, ten years, under `KEYSTORE_PASSWORD`) signs every CSR-enrolled device certificate: `CN=PinVault Client: <clientId>` (the CSR's own subject is ignored), a random serial, `notBefore` an hour back for device clocks, `CLIENT_CERT_TTL_DAYS` (90) of lifetime, client-auth only. The truststore holds the CA, so enrollment and renewal no longer restart the mTLS listeners; revocation is checked in the database (`client_identities`, migration V12) at renewal.
- **`POST /api/v1/client-certs/renew`** on every Config API listener: with a client certificate presented, it must be valid and carry the CSR's key; without one, the body's `clientId` must be registered with the CSR's key. Revoked, unknown or mismatched identities all get the same `403 reenroll_required`. Rate-limited per source and client id; refusals are audited as `client_cert_auth_failed` (summarised per minute like invalid admin keys), issuances as `client_cert_issued` / `client_cert_renewed`.
- Enrolling a revoked client id is refused (`403 revoked`) before the token is spent — `client_certs` used to be re-inserted, which silently un-revoked it. `DELETE /api/v1/client-certs/{id}` revokes the identity too.
- `GET /api/v1/client-certs` rows carry `notAfter`, `renewCount` and `keyType` (`csr` | `p12`); the dashboard's mTLS tab shows them.
- **Recovery door** (`RECOVERY_PORT`, default `PORT+3`, 8083 in Docker): a TLS listener without client auth that serves only renewal and `/health`. Its certificate is signed by a new **server CA** (`server-ca.jks` + backup key) and reissued 30 days before expiry; apps pin the CA for that port only. `GET /api/v1/recovery-door` and the dashboard's mTLS tab show the port and the two CA pins. Revoking a CSR-enrolled device no longer restarts every mTLS listener.
- `ALLOW_TEST_HOOKS=true` enables `POST /api/v1/test-hooks/client-cert-ttl` for the instrumented tests. The management-port enrollment endpoint stays P12-only.
- **Enrollment policies: one code, many devices, optional approval.** `POST /api/v1/enrollment-policies` `{name, maxDevices (1–10000), validDays (1–365), requireApproval (default true)}` returns the code once (25 characters of Crockford base32 in five groups, 125 bits; case, dashes and look-alike letters are forgiven); only its SHA-256 is stored (migration V13: `enrollment_policies`, `enrollment_requests`). Each device that enrolls with it gets its own client id `<name>-<6 chars>` and a certificate over its own key (CSR only, `400 csr_required` otherwise); the device limit is taken by one conditional update, so racing devices never get more certificates than the policy allows. With `requireApproval` the device gets `202 {status: "pending", requestId, clientId}` with `Retry-After: 15` and asks again with `{requestId, csr}` — the CSR must be signed by the key the request was made with (`403 enrollment_request_mismatch`); an administrator decides with `GET /api/v1/enrollment-requests?status=pending` and `POST /api/v1/enrollment-requests/{id}/approve` or `…/reject` (`403 enrollment_rejected` to the device). Waiting devices per policy are capped at its device limit (`429`), approvals never exceed it, and a device that already has an active identity is shown as such (`heldBy`) and can be approved only after that one is revoked. `POST /api/v1/enrollment-policies/{id}/stop` ends the code: no new devices, waiting ones are turned away, approved ones still pick their certificates up; a stopped or expired code is answered like a used token (`401`). Audited: `enrollment_policy_created` / `_stopped`, `enrollment_request_pending` (webhook: a device is waiting) / `_approved` / `_rejected`, `client_cert_issued` with the policy; refusals anyone holding the code can cause go through the per-minute summary as `client_cert_enroll_refused`. The dashboard's mTLS tab has *Enrollment policies* (the code is shown once, with a QR code generated in the page) and *Devices awaiting approval* (refreshed every 10 s while open).
- **Applications without a code.** *Devices awaiting approval* has a switch, *Applications without a code* (`GET` / `PUT /api/v1/enrollment-open` `{"enabled": …}`, audited as `enrollment_open_changed`). While it is on, a device that enrolls with only its device id gets `202 pending` and waits for an administrator like a device with a code; the switch takes precedence over `ENROLLMENT_MODE=open`. Off, such a device gets `403 Token required`, and the requests already waiting can still be decided. Migration V14: one policy row with `open_applications` collects them, `accepting` follows the switch. Bounds: `OPEN_ENROLLMENT_RATE_LIMIT` (20 new applications per source address per 10 minutes, `429 too_many_applications`), `OPEN_ENROLLMENT_MAX_PENDING` (50, `429 too_many_pending_requests`), and `ENROLLMENT_REQUEST_TTL_HOURS` (24) for every waiting request, code or not: unanswered, it is marked expired and the device gets `410 enrollment_request_expired`. Requests carry `verificationCode` (from the CSR's key, computed exactly as the library does), `openApplication`, and `sameDevicePending` when the same device id has another request waiting (a reinstall); `GET /api/v1/enrollment-mode` gains `openApplications`.
- **Forgetting a revoked identity.** A revoked client id stayed revoked for good, so a device enrolled in open mode — whose client id is its own device id — could never enroll again. *Forget identity* on a revoked row of the dashboard's client certificate list (`POST /api/v1/client-certs/{id}/forget`, `409 not_revoked` for an active one, audited as `client_identity_forgotten`) frees the client id. Every key a client id enrolls with is now recorded (migration V15: `client_keys`, filled from `client_identities`); forgetting retires them all, then deletes the identity's rows in the same transaction. A certificate over a retired key is refused on every mTLS request (`RevocationGate`, `403 reenroll_required`) even though its client id may be enrolled again, and a retired key is refused at enrollment under any client id (`403 revoked`, before a token or a code is used).
- The dashboard's audit log can filter and names the device actions recorded since the CSR work (`client_cert_*`, `device_key_*`, `device_id_refused`, `test_hook_used`, the enrollment-policy actions); `DashboardGovernanceLabelsTest` guards them.

### Security fixes

- **An enrollment token yields one certificate.** The token was checked in one statement and marked used in another, so requests racing with a stolen token could all pass the check: the attacker and the real device both got a certificate, and the real device never saw the `401` that would have exposed the theft. The token is now spent in a single conditional update right before anything is issued; the losers of a race get `401`. A malformed CSR no longer spends the token. The management-port copy of the endpoint spends it the same way and now also refuses revoked client ids (it used to re-insert them, un-revoked).
- **Device E2E keys can no longer be set by anyone (audit M-2).** `POST /api/v1/vault/devices/{deviceId}/public-key` accepted any key for any device id, so a stranger could swap in a key and read what the server then encrypted for that device. Now a presented client certificate must belong to the device (`403 device_identity_mismatch` otherwise); without one (a TLS listener) the first key is kept and a different key needs the device's token for an `end_to_end` file of that scope (`X-Vault-Key` + `X-Vault-Token`, otherwise `409 key_change_requires_proof`). The library sends that token along on its own when the app has one, so clearing the app's data keeps working. New: `DELETE /api/v1/vault/devices/{deviceId}/public-key` and its scoped management twin to free a slot; registrations, replacements, refusals and resets are audited (`device_key_registered`, `device_key_replaced`, `device_key_refused`, `device_key_reset`).
- **A revoked device is cut off at once.** The mTLS listeners trust the client CA, so a revoked CSR certificate kept passing the handshake and — revocation being checked only at renewal — kept fetching configs and files for up to `CLIENT_CERT_TTL_DAYS`. Every request on an mTLS Config API listener now checks the identity behind the presented certificate and answers a revoked one `403 reenroll_required` (audited as `client_cert_revoked_refused`, summarised per minute).
- **One active identity per device id.** The `deviceUid` sent at enrollment is self-reported, yet token_mtls and E2E key registration trusted it to tie a certificate to a device: an enrolled party could claim another device's id and act for it. An enrollment claiming a device id that another active client id holds is refused with `409 device_already_enrolled`, before the token is spent; re-enrolling the same client id still replaces it.
- **Request bodies on device endpoints are capped at 64 KB.** They were read in full before any check — 100 MB was buffered and only then refused. A larger declared length gets `413` unread, a body without a declared length `411`; on the recovery door too, where the rate limit ran after the read.
- **Client and device ids are restricted to letters, digits, `.`, `_`, `:` and `-` (at most 64).** A client id was printed unescaped in the dashboard's mTLS tab, so under `ENROLLMENT_MODE=open` a device id carrying markup ran script in the administrator's browser; it could also add name parts to the certificate subject. The dashboard escapes it, enrollment, token minting and the test hook refuse other characters (`400 invalid_client_id` / `invalid_device_uid`), and subjects are built part by part.
- **On an mTLS Config API, `X-Device-Id` must belong to the client certificate.** The header picks the per-device host ACL of a config fetch and the device a `token` vault download is checked against, and it was taken at its word: an enrolled device could send another device's id and read the pins that device's ACL grants, or download with a token taken from it. A header naming a device other than the certificate's (its client id, or the `deviceUid` it enrolled with) is now refused with `403 device_identity_mismatch` on every request (audited as `device_id_refused`, summarised per minute). The library always sends the id it enrolled with. The management-port enrollment now records `deviceUid` too, under the one-identity rule, so its certificates pass. On a TLS listener the header stays the device's own claim.
- **E2E key registration over TLS is bounded.** It asks for no credential, and any device id with any text as a key was stored, audited and pushed to the webhook — a source could fill the table and the notification channel at will. Now only RSA keys of 2048–4096 bits are stored (re-encoded; `400 invalid_public_key`), device ids follow the identifier rule (`400 invalid_device_id`), a source address writes at most `DEVICE_KEY_RATE_LIMIT` keys per 10 minutes without a client certificate (default 30, `0` = off; `429`), a Config API holds at most `DEVICE_KEY_LIMIT` keys (default 100 000; a new device beyond it gets `503`), and `NOTIFY_EVENTS=*` no longer pushes the routine `device_key_registered` (name it to receive it).

## 2.1.0 — 2026-10-02 — Optional security layers

Every item below is **opt-in**. A client and a server that configure none of them behave exactly as before, and each side keeps working with an older version of the other. See [`SECURE_OPERATIONS.md`](SECURE_OPERATIONS.md) for which layers to enable and the operational runbooks.

### Library (opt-in)

- **Several trusted signing keys.** `ConfigApiBlock.Builder.signaturePublicKeys(vararg)` (also a `List` overload for Java): a config signed by any of them is accepted. Ship an offline backup key in the app and a lost or stolen primary can be replaced on the server without an app update. `signaturePublicKey(key)` still works and means a one-key list.
- **m-of-n signatures.** `requiredSignatures(n)`: every config (and every vault file of the block) needs valid signatures from `n` *distinct* trusted keys. The envelope carries them in the new optional `signatures: [{keyId, signature}]` field; vault downloads in `X-Vault-Signatures: <keyId>:<sig>,…`. Keys are parsed and compared in canonical form, so two spellings of one key never count as two signers.
- **Signing-key sets: rotation and revocation over the air.** `recoveryPublicKeys(vararg)` + `requiredRecoverySignatures(n)`: offline recovery keys sign a versioned list of signing keys (`{"type":"pinvault-signing-keys","version":N,"keys":[…],"requiredSignatures":m}`), delivered in the envelope's optional `signingKeys` field. A device applies a newer set and from then on trusts exactly the keys it lists — a key left out is revoked. Sets are persisted in their own encrypted file (`pinvault_signing_keys.xml`, excluded from backup, kept across `PinVault.reset()`), re-verified against the app's recovery keys on every load, can raise but never lower the app's signature count, and may not name a recovery key as a signing key. A forged or malformed set fails the whole response.
- **`PinVault.signingStatus(configApiId)`** → `SigningStatus`: trusted key ids, required signature count, applied key-set version, recovery key ids and the keys that signed the last accepted config. `null` for unsigned blocks and blocks served by a custom `CertificateConfigApi`.

### Library (behaviour)

- **Encrypted storage moved to the Android Keystore.** Google deprecated androidx.security's EncryptedSharedPreferences in April 2025. The four stores now use `SecurePreferences`: values sealed with AES-256-GCM, names hidden with HMAC-SHA256, both keys generated in the Android Keystore and never leaving it (EncryptedSharedPreferences held its data keys in app memory). Each store type has one fixed file (`pinvault_secure_config.xml` holds every Config API block, each in its own namespace), so the bundled backup rules cover any Config API id (audit N-23) and the build-time warning about uncovered ids is gone. On the first start the 2.0.x files are read once with the old library, moved and deleted: configs, client certificates, key sets and cached vault files carry over. Downgrading to 2.0.x afterwards starts from scratch (MIGRATION.md). The pre-Android-12 backup rules now also exclude the vault file store's version map and `vault_files/`, as the Android 12+ rules already did.
- **`PinVaultBackendReporter.pinnedClient(host, pins)`** — a client pinned to pins the app already ships (self-signed certificates included) whose handshakes raise no connection events, for sending reports over HTTPS without an unpinned client.
- **P12 passwords are negotiated per download.** Enrollment and host client certificate requests send `X-PinVault-Features: p12password`; a bundle that arrives with `X-P12-Password` is checked with that password and re-wrapped with the block's `clientKeyPassword` before it is stored, so an app no longer has to carry a password chosen on the server. `EnrollmentResult.p12Password` (constructor overloads kept for Java). Servers that send no password work as before.
- **A pin can name an issuer.** A pin matches the leaf's key, as before, or the key of an issuer certificate in the served chain, as with OkHttp's `CertificatePinner` and Android's network security config; a host pinned to its CA survives a leaf renewal with a new key. The library does no CA validation, so an issuer pin counts only when the leaf validly chains to that issuer (PKIX, with the pinned certificate as the only trust anchor): a forged leaf with the genuine intermediate appended is refused. The server used to publish an intermediate as a fetched host's "backup" pin that devices could never match.
- **The same signed config served twice is `AlreadyCurrent`, not a replay.** A backend that signs once per change (HSM/KMS signer, signature cache, CDN) serves byte-identical configs; the updater used to reject every repeat with "Config replay rejected" because it compared `issuedAt <= stored` before change detection. An equal `issuedAt` with the same hosts, versions and pin sets is now a no-op (its force flag is not re-applied); an equal `issuedAt` with different content and any older `issuedAt` are still rejected.
- **Android 7 (API 24–25) no longer crashes when per-device vault files are configured.** The device key's PEM was built with `java.util.Base64`, which exists only from API 26; the init coroutine died with `NoClassDefFoundError` and took the app with it. Found by running the instrumented tests on an API 24 emulator (minSdk); `lintDebug` reports it as `NewApi`, but lint was never run.
- **`init` never crashes the app.** An unexpected failure during initialisation, including an API the device lacks (`LinkageError`), now ends as `InitResult.Failed` with pinning still fail-closed, instead of an exception thrown on a background thread by the callback variants. Device key registration failing that way only disables per-device vault files.
- The consumer ProGuard rules keep the library's class names, so a minified app logs `D/DynamicSSLManager: Pin verified ✓` instead of `D/f: …` (Timber tags lines with the calling class). Members are still shrunk and renamed.
- Signed-config requests send `X-PinVault-Features: redelivery,multisig,keyset` so a backend can tell which clients understand the new fields.
- Config signature failures name the reason: "1 of 2 required signatures valid", "signed by a key revoked by signing-key set v3".

### Demo server (opt-in)

- **Pluggable signers** — `CONFIG_SIGNERS=local` (default: the key file, as before) `| pkcs11 | command`, comma-separated for several signatures. `pkcs11` signs with a key generated inside an HSM as sensitive, never-extractable and sign-only — no decrypt, unwrap, sign-recover or derive (SunPKCS11; `PKCS11_LIBRARY`, `PKCS11_PIN`, `PKCS11_SLOT_INDEX`, `PKCS11_KEY_LABEL`, `PKCS11_GENERATE_KEY`). `command` runs an external signer — a cloud KMS CLI, Vault transit, a remote signing service — with the bytes on stdin (`SIGNER_COMMAND`, `SIGNER_PUBLIC_KEY[_FILE]`, `SIGNER_INPUT=payload|digest`); every signature it returns is verified before use. Named signers (`local:next`, `command:kms`) take suffixed variables.
- **Signature cache** — `CONFIG_SIGNATURE_CACHE=true`: identical content is signed once and served identically until half its TTL has passed; the pin store pre-signs every publish, so the signer is called when an operator publishes, not when devices poll. Cached envelopes go only to clients that announce `redelivery`; the cache is dropped on every admin write, and `issuedAt` is monotonic.
- **Signing-key sets** — `RECOVERY_PUBLIC_KEYS` (+ `RECOVERY_REQUIRED_SIGNATURES`) enables `PUT /api/v1/signing-keyset`: the server checks an offline-signed set the way a device will (recovery signatures, type, increasing version, parseable keys, no recovery key as signing key) and refuses a set that its own active signers could not satisfy, then attaches the latest set to every signed config. `GET /api/v1/signing/status`, `GET /api/v1/signing-keyset`. Regenerating the local key is refused while a set is active.
- **Named admins** — `ADMIN_KEYS=name:sha256hex,…` (or `ADMIN_KEYS_FILE`): personal admin keys, of which the server holds only hashes. `API_KEY` keeps working as the admin `admin`. `GET /api/v1/admin/me`.
- **Audit log** — every admin write is recorded with who, when and what (pin changes as a host-by-host diff), in an append-only table (`V10__audit_log`, UPDATE/DELETE triggers) where each row carries the SHA-256 of the previous one. `GET /api/v1/audit-log`, `GET /api/v1/audit-log/verify`. Invalid API keys are recorded (one entry per source per minute); expiring certificates once a day per host.
- **Webhook notifications** — `NOTIFY_WEBHOOK_URL` (+ `NOTIFY_WEBHOOK_SECRET` for an `X-PinVault-Signature: sha256=<HMAC>` header, `NOTIFY_EVENTS` to filter): security events are pushed as they happen, Slack-compatible `text` included, with retries. `GET /api/v1/notifications`, `POST /api/v1/notifications/test`.
- **Two-person approval** — `PIN_CHANGE_APPROVALS=2` (or more): pin, force, certificate, bootstrap-pin and signing-key changes become change requests (`202 {pendingApproval, changeRequestId}`) that another *named* admin must approve; the server then replays the exact request as the requester. No self-approval, the shared `API_KEY` cannot approve, a request made against pins that have since changed is refused as stale, requests expire after `APPROVAL_TTL_HOURS`. The device-facing Config API ports refuse pin writes in this mode. `GET/POST /api/v1/change-requests…`.
- **Live certificate gate** — `PIN_LIVE_CHECK=warn|enforce`: a new or changed pin set must be one devices accept for the chain the host serves right now: its leaf's pin, or the pin of an issuer the leaf validly chains to. `enforce` answers 422 with what the host serves; `?liveCheckOverride=<reason>` stores it anyway (audited, notified) unless `PIN_LIVE_CHECK_ALLOW_OVERRIDE=false`. `LIVE_CHECK_HOST_MAP` maps names the server cannot resolve (and wildcard entries) to a probe address. `POST /api/v1/pins/live-check` is a dry run for the dashboard.

- Hardening from an automated multi-agent review before release (AI reviewers that had not written the code; not a third-party audit): the approval gate decides on the path as routing resolves it, the shared `API_KEY` cannot request gated changes, undescribable or non-UTF-8 requests are refused, the signature cache can no longer serve an older `issuedAt` than a device applied, invalid-key attempts are summarised, decided change requests drop their stored bodies, the command signer runs without the server's secrets and is killed with its children on timeout, and `config-apis/start|stop` are gated too (see `SECURITY_AUDIT.md` N-33…N-39).

### Demo server (behaviour)

- Dependencies with published advisories moved to the newest patch of the same line: Netty 4.1.116 → 4.1.138 (via `netty-bom`; Ktor 3.0.3 brought the old one), logback 1.5.12 → 1.5.38, Jackson 3.1.0 → 3.1.7 (via `jackson-bom`; Flyway brought the old one), Bouncy Castle 1.79 → 1.86. An OSV scan of the runtime classpath reported 60 known advisories before and none after; the library's own runtime dependencies had none.
- The dashboard script is split into seven files under `static/js/` (core, i18n, hosts, sections, governance, vault, main), loaded in order; the code is unchanged.
- **The management API can listen over TLS.** `MANAGEMENT_HTTPS_PORT` adds a TLS connector to the management application, with the server's own certificate (the one apps pin). The sample host publishes plain HTTP on this machine only (`HOST_HTTP_BIND=127.0.0.1`) and the TLS port to the network: devices send their reports pinned, remote admins reach the dashboard without the API key crossing the network in the clear. The sample app's telemetry moved there, so it no longer needs a cleartext exception. The sample host's container runs as an unprivileged user.
- **The vault password can be changed, and a wrong one fails loudly.** `VAULT_AT_REST_PASSWORD_PREVIOUS`: at startup, at_rest and per-device files that open only with the previous password, or with the demo password when the variable was unset, are re-encrypted under `VAULT_AT_REST_PASSWORD`. A file that no password opens is logged and its downloads fail. It used to be served as its ciphertext, and the vault signature, computed over what is served, made devices store it as the file. The admin listing no longer decrypts every file to report sizes. The sample host's `setup.sh` generates `VAULT_AT_REST_PASSWORD`.
- **Per-device (`end_to_end`) vault files are encrypted on disk.** The server encrypts each download for one device, so it needs the content — but it used to keep it in the clear, and `end_to_end` could not be combined with `at_rest`. It is now stored under the at-rest key (`VAULT_AT_REST_PASSWORD`), and files stored before are encrypted at startup. Docs call the mode what it is: per-device encryption; the server sees the content.
- **The keystore password never leaves the server.** `KEYSTORE_PASSWORD` also wrapped every device P12, so any app doing mTLS enrollment had to carry the password that protected the server's TLS keys — or the server stayed on `changeit`. Device P12s now go out with a one-off password when the client asks for one (`X-P12-Password`), otherwise with `CLIENT_P12_PASSWORD` (default `changeit`, for older library versions and manual installs). Uploaded host client certificates are stored under `KEYSTORE_PASSWORD` and re-wrapped for each download. At startup, keystores written under the old default or under `KEYSTORE_PASSWORD_PREVIOUS` move to `KEYSTORE_PASSWORD`, so setting or changing it on an existing install protects what is already on disk; the sample host's `setup.sh` generates one.
- **A backup pin is a real second key.** A host needs two *different* pins; `[X, X]` is refused. An uploaded certificate gets a stored backup key like a generated one, so it can switch to it; it used to get its chain's issuer or, for a lone certificate, its own pin twice. A host fetched from a URL gets its issuer's pin as the backup, and a site that serves its certificate alone is refused with 422 `reason: no_second_certificate`. The live gate applies the device rule (`PinChain`).
- **Generated certificates keep their backup key.** Host certificates (`generate-cert`, `regenerate-cert`) and the config server's own certificate published a backup pin but threw the backup private key away, so no certificate could ever serve that pin. The key is now stored in `certs/<id>.backup.jks`, a separate keystore, so TLS listeners only ever load the serving key. New `POST /api/v1/hosts/{hostname}/rotate-to-backup` and `POST /api/v1/server-tls-pins/rotate-to-backup` (dashboard: "Switch to Backup Key") reissue the certificate with the stored backup key, prepare a new backup and publish `{old backup, new backup}`. Devices keep connecting without a config refresh, and apps keep connecting to the config server without an update (after a restart). Both are certificate changes for two-person approval. They answer 409 with `reason: no_backup_key` (pins fetched from a URL, certificates generated before this change) or `backup_not_published`. The backup sits next to the primary, so a server whose `certs/` directory was read needs a regenerate instead (`SECURE_OPERATIONS.md`).
- `POST /api/v1/config/{id}/update` runs the same validation, per-host versioning, history and live gate as `PUT /api/v1/certificate-config`; it used to store the body as sent, versions included.
- `GET /api/v1/signing-key` also returns `keyId`, every signer's key and the current key-set version (`publicKey` is unchanged).
- The dashboard no longer resets a host's `mtls` / `clientCertVersion` flags and the scope's force flag when pins are edited.

## Earlier — Security hardening

**Breaking** — this stream of changes flips several "optional" defenses into "required" defaults. See `MIGRATION.md` for the upgrade path.

### Library (breaking)

- **`signaturePublicKey` is now required.** `ConfigApiBlock.Builder.build()` throws unless `signaturePublicKey(...)` is set, or `allowUnsigned()` is called as an explicit opt-out. Closes the silent-disable footgun (H-03).
- **Signed configs must carry `issuedAt` + `expiresAt`** (Unix epoch ms). The library rejects responses where `expiresAt <= now`, `issuedAt <= storedIssuedAt`, or either field is missing. Closes the replay window even when the signature is still cryptographically valid (M-08).
- **Per-host pin enforcement.** Pin lookup is now keyed by hostname (with single-label wildcard support `*.example.com`). A pin entry for host A no longer validates a cert on host B; unknown hostnames fail closed. Pre-V3 the library flattened every host's hashes into one set (H-01).
- **Per-host version monotonicity.** Updater rejects fetched configs whose per-host `version` is lower than the stored value — closes a downgrade attack the prior change-detect logic permitted (M-08).
- **`getClient()` is fail-closed before the first config.** `HttpClientProvider` used to start with (and `reset()` return to) a system-trust `OkHttpClient`, so an app calling `PinVault.getClient()` while a callback-style `init()` was still fetching config sent requests with no pinning at all. The initial/reset client now installs the pinning trust manager over the live config: TLS handshakes are refused until a config is applied and succeed right after, without rebuilding the client. `getClient(settings)` follows the same rule and re-reads the config on every handshake instead of snapshotting it.
- **Enrollment requires `X-P12-SHA256` response header.** Enrollment refuses to install a P12 if the header is missing; previously the check was skipped with a warning (H-05).
- **`PinRecoveryInterceptor` no longer matches exception messages.** Recovery is driven by typed `CertificateException` causes only. Adds a per-host circuit breaker (3 failures in 5 min → 10 min cooldown) so a poisoned backend can't thrash the client (M-03).

### Library (non-breaking)

- Pin-mismatch logs no longer dump the full accepted-hashes list — only a short cert-hash prefix (M-01).
- `ANDROID_ID` auto-enrollment annotated as a soft identifier; production callers should layer Play Integrity / SafetyNet on top (M-02).
- Backup rules exclude `ssl_cert_config_*.xml` and the vault file store so an attacker can't pin-downgrade by restoring a pre-rotation device backup (M-07).
- `CertificateConfigStore` wipes the prefs on parse failure so a corrupt blob can't loop on every load (L-01).
- Dropped the leftover `"changeit"` placeholder from the static-pin init path (M-06).

### Demo server (breaking)

- **`API_KEY` env var is now required to start.** Set `ALLOW_ANONYMOUS_ADMIN=true` to opt out explicitly (dev). Previous behavior silently disabled auth on missing env var — `docker compose up` from the demo file would have shipped an open admin API (C-01).
- **Every signed `/api/v1/certificate-config` response carries `issuedAt` + `expiresAt`.** TTL via `CONFIG_TTL_SECONDS` env var (default 24h). Required by the new library freshness check.
- **`api_key` vault files now actually require `X-API-Key`.** `GET /api/v1/vault/{key}` is allowlisted for devices, and the handler's `api_key` branch was a no-op, so "admin-only" files were served to anyone. The handler now checks the key itself and answers 403 when no `API_KEY` is configured (N-2).
- **Narrower unauthenticated allowlist.** Prefix rules exposed admin reads on the Config API ports: `GET /api/v1/vault/distributions`, `/vault/stats` and `/certificate-config/history/{host}` now require `X-API-Key`. Vault keys named `distributions`, `stats`, `devices`, `report` or `tokens` are rejected on upload (N-3).
- **`ping-remote` no longer runs a shell.** The `{hostname}` path segment was interpolated into `sh -c`; it is now validated and passed to `openssl s_client` as an argument, with the pin computed in-process (N-1).
- **Revoking a client certificate takes effect immediately.** `DELETE /api/v1/client-certs/{id}` removed the certificate from the truststore file, but the running mTLS listeners kept the truststore they were started with, so a revoked device could keep connecting until the next server restart. Revocation now restarts the mTLS Config APIs and mock mTLS hosts, as enrollment already did (N-5).
- **Per-host versions survive delete + re-add.** A host that was deleted and added back restarted at v1. Clients reject per-host version downgrades, so every device that had seen the old versions ignored the re-added host's updates and kept its stale pins. New migration `V7__host_version_watermark` keeps a per-scope high-water mark; `PinConfigStore.save` places re-added hosts above it and every add path reports the stored version.

### Demo server (non-breaking)

- `SIGNING_KEY_PASSWORD` env var enables AES-256-GCM at-rest encryption (PBKDF2-SHA256, 200k iterations) of the ECDSA signing key. Existing plaintext key files are auto-migrated on first startup with the env var set (H-04).
- `DefaultHeaders` plugin installs CSP, X-Content-Type-Options, X-Frame-Options, Referrer-Policy on the management server. Tightens the admin UI's XSS surface (M-05).
- Connection-report endpoint regex-validates `hostname`, `deviceManufacturer`, `deviceModel`. Vault `{key}` parameter regex-validated as defense-in-depth (M-04, L-02).
- Admin web UI escapes server-supplied strings via `esc()` helper before innerHTML interpolation in connection-history, client-device, pin-history, and global-health views (H-02).
- BouncyCastle `bcprov-jdk18on` / `bcpkix-jdk18on` 1.78.1 → 1.79 (L-03).
- Dashboard no longer reports "pins updated", "host added" or "host deleted" after the server rejected the save; only the error toast is shown.
- Dashboard "mTLS client certificates" tab renders again. Its integration snippet referenced an undefined `data.httpsPort`, so the tab always showed the generic error and enrollment tokens could not be generated or certificates revoked from the UI. The snippet now uses the selected mTLS Config API's port.
- **Regenerating the signing key now takes effect in the running server.** `POST /api/v1/signing-key/regenerate` rewrote the key file and reassigned a local variable, but every route had captured the `ConfigSigningService` instance at startup. The dashboard reported success while the server kept signing with the old key, and the rotation only landed at the next restart — silently invalidating every client that had embedded the previous public key. The service now rotates its key pair in place (`regenerate()`), and the response carries `clientUpdateRequired`. Tests: `SigningKeyAndForceUpdateTest`.
- **Per-host `forceUpdate` reaches the client's force gate.** The dashboard only ever sets per-host flags, while the library's "force update or refuse to start" check reads the config-level flag, so a device with a stale forced config still started up happily against an unreachable backend. Served configs are now stamped with `forceUpdate = hasAnyForceUpdate()`.
- The signing key can be rewritten when the key file itself is a mount point. `writeOwnerOnly` renames a temp file over the target, which fails with `EBUSY` on a single-file Docker bind mount: the server refused to start as soon as `SIGNING_KEY_PASSWORD` triggered the at-rest migration, and "regenerate signing key" in the dashboard failed the same way. It now falls back to an in-place write and re-applies 0600. (`SamplePinVaultHost` also mounts the whole `data/` directory now.)
- Removed `static/app.js.bak`, a stale April copy of the dashboard script that the server was serving unauthenticated under `/static/` (it is git-ignored, so it never left this working tree, but a deployed image built from a dirty checkout would have shipped it).
- A blank `SIGNING_KEY_PASSWORD` is treated as unset. Compose files that pass the variable through (`${SIGNING_KEY_PASSWORD:-}`) used to turn an empty value into an empty encryption password.
- `EXTRA_CERT_SANS` env var (comma-separated IPv4 / DNS names) is added to every certificate the server generates. In a container the interface scan only sees the container's own address, so without it Android clients connecting by the Docker host's LAN IP fail hostname verification.

### Library — Trust manager dynamism

- **`PinVault.applyTo(builder)` trust manager is now actually dynamic.** Previously the trust manager snapshotted `pinMap` at the time of the call, so config swaps from `updateNow()` / WorkManager never reached requests issued through an externally maintained `OkHttpClient`. The KDoc claimed dynamic behavior but the implementation was static, and the recovery interceptor couldn't compensate when a rotation kept old pins valid for the still-unrotated cert. The dynamic trust manager re-reads `clientProvider.currentConfig` on every TLS handshake; the old snapshot overload has been removed and internal callers (`buildClient`, `buildBootstrapClient`) pass constant lambdas.
- **`applyTo(builder)` is now fail-closed when no config has loaded yet.** The previous early-return left the consumer's builder untouched and warned "system defaults" — silent unpinned traffic during the brief window between `setup()` and `executeInit()` on the callback init path. The dynamic trust manager is now installed unconditionally; its first handshake refuses to connect until init completes.

### Library — Additional security hardening

- **`forceUpdate` flag now persists across restarts.** `CertificateConfigStore.save()` did not write the flag and `load()` hardcoded `false`, so a backend that pushed `forceUpdate=true` lost the guard after every process restart — an attacker blocking the backend at that moment could keep a revoked config in service.
- **Constant-time P12 hash comparison in enrollment.** `validateP12` compared the server's `X-P12-SHA256` header against the locally computed hash via `String.equals`, which short-circuits on first byte mismatch. Switched to `MessageDigest.isEqual` on decoded bytes.
- **TLD-level wildcard patterns refused.** `PinHostMatcher.match` now skips `*.com`, `*.tr`, etc. (suffixes without a dot). Keeps a misconfigured single entry from authorizing every domain under a TLD and silently re-opening the H-01 cross-host reuse path.
- **Recovery circuit-breaker no longer reset by a single success.** `PinRecoveryInterceptor.recordSuccess` used to wipe the per-host failure counter, letting a partial MITM keep the 3-in-5-minutes breaker permanently disarmed by interleaving forged handshakes with legitimate ones. Now a no-op; the counter only ages out through the existing window.
- **Connection-listener dispatch queue is bounded** (256 entries, `DiscardPolicy`). A consumer-supplied listener that blocks (e.g. a synchronous POST to an unreachable telemetry endpoint) used to let handshake events accumulate without limit.

### Library — Recovery retry

- **Pin-mismatch recovery retries on the caller's own client.** `PinRecoveryInterceptor` always re-issued the request through PinVault's internally managed client, so a consumer client built with `applyTo(builder)` lost its `Dns`, interceptors and timeouts on the retry: an app resolving private hostnames through a custom `Dns` saw the recovery attempt die with `UnknownHostException` even though the refreshed pins were correct. The retry now runs on the intercepted chain, which keeps the caller's configuration and picks up the new pins through the dynamic trust manager; the internally managed client (built against a config snapshot) still falls back to the freshly swapped client.
- **The fallback attempt no longer hides the original error.** When the retry on the caller's chain failed and the fallback on the library's internal client failed too, the interceptor threw the *fallback's* exception. Because that client does not carry the caller's `Dns`, the app was handed an `UnknownHostException` in place of the pin mismatch it actually hit — the same `Dns` gap as above, one layer down. The original exception is now rethrown with the fallback's failure attached via `addSuppressed`, so the diagnosis is right and the fallback attempt stays visible in a stack trace. Tests: `PinRecoveryInterceptorTest`.
- **An expired server certificate no longer triggers a config refresh.** `DynamicSSLManager` reported a leaf outside its validity window as a plain `CertificateException`, which `isPinMismatch` could not tell apart from a real pin mismatch: every request to a host with an expired certificate refetched the pin config, retried, failed again with the retry's error instead of the real reason, and pushed the per-host recovery circuit breaker towards its cooldown — for a condition no config can repair. The trust manager now throws the new public `CertificateValidityException` (still a `CertificateException`, so trust-manager semantics are unchanged) and the interceptor lets it pass straight through to the caller. A bare `CertificateException` cause still recovers as before.

### Library — Empty config is a rejection, not a no-op

- **An empty `pins` list is treated as a change and fails validation.** `SSLCertificateUpdater.updateNow` decided "nothing changed" from three clauses that are *all* false when the remote and the stored pin sets are both empty, so it returned `AlreadyCurrent` and never reached the "config must contain at least one pin entry" check. `init` then reported `Ready(v0)` and the app showed itself as configured while not a single host was pinned. An empty remote config now always routes into validation and comes back as `Failed` / `InvalidPinFormatException`; a stored config is left untouched, so a device that already holds good pins keeps them. `validateConfig` raises `InvalidPinFormatException` for that case instead of the `require(...)` it used to be, so a now-reachable rejection carries the library's own type (the message, and therefore `UpdateResult.Failed.reason`, is unchanged). Tests: `SSLCertificateUpdaterTest`.

### Library — Connection events

- **`PinVaultConnectionEvent.ConfigUpdate` added.** Sealed class now carries config-rotation outcomes (`UPDATED` / `UNCHANGED` / `FAILED`) on the same listener pipe as handshake events. `notifyUpdateResult` emits both on the legacy `OnUpdateListener` and on `PinVaultConnectionListener.onEvent`. `when` expressions over `PinVaultConnectionEvent` need a new branch — the sealed-class doc already advertised this kind of extension.

### Reporter — Throttling and filtering

- **`reportSuccessEvents: Boolean`** (default `true`, legacy behavior). Set to `false` to POST only anomaly events — pin mismatches and config-update failures. Healthy handshakes and successful config rotations are suppressed entirely.
- **`dedupWindowMs: Long`** (default `0`, legacy behavior). When > 0, duplicate "healthy" Connection reports for the same `(hostname, pinVersion, serverCertPin)` tuple inside the window are dropped. ConfigUpdate events are not deduped — they are already periodic.
- **`reportToPinVaultBackend(...)` DSL helper** exposes the same two parameters.

### Reporter — Config-update endpoint

- Reporter POSTs `PinVaultConnectionEvent.ConfigUpdate` events to a new endpoint, `POST /api/v1/connection-history/config-update-report`, with status (`config_updated` / `config_unchanged` / `config_update_failed`), pinVersion, device fields, and optional `failureReason`.

### Library — Runtime listener registration

- **`PinVault.setConnectionListener(listener: PinVaultConnectionListener?)`** added. Lets callers attach (or detach) a listener after `init` has returned — needed for production reporter setups where the reporter's own `OkHttpClient` must be pinned via `PinVault.applyTo(...)`, which itself requires the active config to already be loaded. Builder-time `onConnectionEvent(...)` is unchanged; this new method is purely additive. README documents both "same-host as Config API" and "separate management host" pinning patterns.

### Demo server — Config-update reports

- New route `POST /api/v1/connection-history/config-update-report` accepts reporter payloads, reuses the existing `connection_history` table with `source='config_update'`, and applies the same M-04 identifier validation as `/client-report`. Whitelisted in `ApiKeyAuth` so unauthenticated clients can report (matches `/client-report`).

### Library — Dead settings and mismatched labels (breaking)

- **`ConfigApiBlock.Builder.enrollmentToken(token)` removed.** The token was stored on the block and never read — neither `PinVault.enroll` nor `PinVault.autoEnroll` consulted it — so a builder-time token silently did nothing while looking like enrollment was configured, and a single-use secret sat in a process-lifetime config object. Pass it at the call site instead: `PinVault.enroll(context, token)` (or `PinVault.autoEnroll(context)` for deviceId-based enrollment). `ConfigApiBlock.enrollmentToken` is gone from the data class, builder, `equals` and `hashCode`.
- **`wantPinsFor(...)` now actually reaches the server.** The block stored the host list and `DefaultCertificateConfigApi.fetchScopedConfig` was implemented, but `SSLCertificateUpdater.updateNow()` always called the unscoped `fetchConfig`, so `?hosts=` and `X-Device-Id` were never sent and the server returned every pin it had — the least-privilege scoping was inert. A block that declares `wantPinsFor` now fetches through `fetchScopedConfig(currentVersion, hosts, deviceId)`; blocks that declare nothing keep the legacy call. The device id comes from the new internal `DeviceIdentity` helper (ANDROID_ID), the same source `PinVault` sends as `deviceUid` at enrollment, so the server-side ACL key matches.
- **`isEnrolled` / `unenroll` / `enrolledClientCN` read the label `enroll` writes.** All three defaulted to `ClientCertSecureStore.DEFAULT_LABEL` while `enroll`/`autoEnroll` default to the Config API block's `clientCertLabel`. With a custom `clientCertLabel(...)` the certificate was written under one key and queried under another: `isEnrolled` returned false right after a successful enrollment and `unenroll` deleted nothing. All four paths now resolve the default the same way.

### Library — Unenroll actually unenrolls

- **`PinVault.unenroll` clears the in-memory client key.** It deleted the P12 from encrypted storage but left the `KeyManager` built at enrollment time loaded in `DynamicSSLManager`, so the device kept authenticating to mTLS hosts until the process restarted. `DynamicSSLManager.clearClientKeystore()` (the inverse of `loadClientKeystore`) drops the default and per-host key managers, and `unenroll` calls it for every Config API block and re-publishes the config so the next request presents no client certificate. Pinning itself is untouched.

### Library — Documentation

- **`getClient(HttpConnectionSettings)` documents that it has no pin-recovery.** Unlike `getClient()` and `applyTo(builder)`, this overload installs pinning only: a pin mismatch surfaces as an SSL exception and PinVault does not auto-refresh the config and retry. Behaviour unchanged; the gap was simply undocumented.

### Demo server — `token_mtls` vault policy works

- **`token_mtls` files were unreachable.** `extractClientCertCn` read a `TLSPeerPrincipal` call attribute that nothing populated, so it always returned null and every `token_mtls` request answered 401 even with a valid client certificate — an advertised policy that was dead. The new `route/ClientCertIdentity.kt` reads the verified peer certificate off the Netty channel's `SslHandler`, so the policy now enforces what it promised: a valid per-device token **and** a client-authenticated connection whose certificate belongs to that device. Match rule: the CN's `PinVault Client: ` prefix is stripped and compared to `X-Device-Id` (auto-enrollment, where the client id is the ANDROID_ID), falling back to `client_certs.device_uid` recorded at enrollment (token enrollment, where the client id is admin-chosen). Revoked certificates are rejected. `CertificateConfigRoute`'s cert-based deviceId fallback for ACL scoping shares the same helper and is no longer inert.
- **`token_mtls` is selectable in the dashboard.** The vault upload form offered only `token` / `public` / `api_key`.

### Demo server — Missing endpoint and header

- **`GET /api/v1/client-devices?configApiId=` added.** The dashboard's Device-ACL manager called this endpoint, no such route existed, and the failure was swallowed — the "enrolled devices" table was always empty, so per-device host ACLs could not be assigned from the UI. The new route (X-API-Key protected) lists devices keyed by the identifier the ACL itself uses (`X-Device-Id` / ANDROID_ID), merging certificates issued at enrollment with devices seen in connection reports for hosts in that scope.
- **Management-port enrollment sends `X-P12-SHA256`.** `POST /api/v1/client-certs/enroll` on port 8090 returned the P12 without the integrity header while the Config API copy sent it. The library refuses to install a P12 with no header (H-05), so a client pointed at the management port failed enrollment outright.
- **Global force-update endpoints accept `?configApiId=`.** `POST /api/v1/certificate-config/force-update` and `/clear-force` are mounted on the management server under the fixed `default-tls` scope, so an admin UI button could only ever act on that one Config API. They now take an optional scope parameter, defaulting to the route's own scope.
- **`GET /api/v1/health` answered 500 on every call.** The response was built from nested `mapOf(...)` with mixed `String` / `Int` / `Map` values, which kotlinx.serialization refuses ("Serializing collections of different element types is not yet supported"). Nothing exercised it — the container probe uses the bare `/health` and the dashboard did not call it — so the failure went unnoticed until the new certificate-expiry card started reading it. The payload is now built from serializable `ServerHealth` / `ConfigApiHealth` / `CertHealth` types; the JSON shape is unchanged from what the endpoint was meant to return.

### Demo server — Enrollment tokens hashed at rest (breaking for API consumers)

- **`enrollment_tokens.token` now stores SHA-256(plaintext), not the plaintext.** A database dump — or `GET /api/v1/enrollment-tokens`, which listed the values verbatim — handed over usable enrollment credentials. The plaintext now exists exactly once, as the response of `POST /api/v1/enrollment-tokens/generate`; validation hashes the presented token and looks it up. The listing returns a masked prefix (`AbC12dEf…`) plus a new `masked: true` field, matching how vault access tokens already work. New migration `V8__enrollment_token_hash` adds `token_prefix` and marks pre-migration plaintext rows used, since they could never match a hash lookup again — re-mint any token still in flight during the upgrade.

### Demo server — API documentation

- **Swagger UI at `/docs` renders again.** `docs.html` loaded swagger-ui from `unpkg.com` and ran an inline `<script>`, both blocked by the server's own `script-src 'self'` CSP, so the page was blank. The dist files are vendored under `static/vendor/` (swagger-ui 5.33.0) and the init code moved to `static/docs.js`; the CSP is unchanged.
- **`static/openapi.yaml` rewritten.** It documented 15 of ~80 endpoints and declared a `currentVersion` query parameter on `/api/v1/certificate-config` that the server does not read (it reads `hosts` and `signed`).

### Demo server — mTLS trust refresh and host pin versions

- **A newly generated or uploaded client certificate is trusted immediately.** `POST /api/v1/client-certs/generate` and `/upload` wrote the certificate into the truststore file and stopped there, but a running mTLS listener holds the truststore it was handed at start — so a client connecting with the P12 the operator had just downloaded was rejected with "certificate unknown" until the server was restarted. Enrollment and revocation already restarted the listeners; all four paths now go through one helper (`refreshMtlsTrust` in `Main.kt`) that restarts the mTLS Config APIs and the mock mTLS hosts against the current truststore.
- **`toggle-mtls` and `upload-client-cert` bump the host's pin version.** Both wrote `mtls` / `clientCertVersion` into the config without moving the version. The client's change detection is per-host version based, so a device that already held the config answered `AlreadyCurrent` in `SSLCertificateUpdater.updateNow` and never ran `syncHostClientCerts` — the host-specific certificate reached only devices whose data had been wiped. Both endpoints now increment the host's `version` (watermark semantics in `PinConfigStore.save` unchanged), record the stored version in the pin history, and report it in the response. Tests: `HostMtlsVersionBumpTest`.
- **`GET /api/v1/enrollment-tokens` reports expiry.** `EnrollmentTokenStore.validate` has always honoured `expires_at`, but the listing did not expose it, so an expired token was indistinguishable from a fresh one. Rows now carry `expiresAt` and a server-computed `expired` flag (an absent or unparseable value means "no expiry", the same rule `validate` applies). Tests: `EnrollmentTokenStoreTest`.
- **`PUT /api/v1/certificate-config` and the per-host force endpoints accept `?configApiId=`.** Same reason the global force endpoints already did: the management server mounts these routes under the fixed `default-tls` scope. Deliberately *not* mirrored on the `GET`, which is in the unauthenticated client allowlist — a scope parameter there would let a device on one Config API port read another scope's pins.

### Demo server — Dashboard

- **Host add / edit / delete write the Config API that is actually selected.** `loadConfig()` always read `GET /api/v1/certificate-config?signed=false` and `saveFullConfig()` always wrote `PUT /api/v1/certificate-config`, both of which resolve to `default-tls` on the management server. With any other Config API open, "+ → Manual", "Edit pins" and "Delete host" therefore read and rewrote the default scope: hosts landed in the wrong Config API and the default scope's pin list was silently modified. Both now use the selected scope (`GET /api/v1/config/{id}`, which the host detail view already used, and `PUT …?configApiId=`), as does the per-host force-update toggle. The "+" button reloads the target scope's config before opening the form — the manual tab submits the whole pin list, so a stale scope would have copied one Config API's pins into another.
- **The "Client certificates" tab renders its enrollment-token list.** `renderConfigApiDetail` rewrites `#content` with the header and tab bar as soon as the tab function returns, but `loadEnrollmentTokens` resolved `#enrollment-token-list` *before* its fetch — that node was detached by the rewrite, so the fill went nowhere and the list appeared only right after "Generate token" / "Revoke". The container is now resolved after the fetch, which finds the rewritten node. (Awaiting the fill inside `renderMtlsSection` instead would work too, but it holds the rewrite open long enough to wipe text typed into the client-id field in the meantime.)
- **Expired enrollment tokens are labelled "Expired" instead of "Pending".** The status column read only the `used` flag, so a token the server would refuse was listed as available. Uses the new `expired` field; the cell's tooltip shows the expiry instant.
- **Vault file policy is editable from the UI.** `PUT …/vault/{key}/policy` existed with no way to reach it; changing a file's access policy or encryption meant re-uploading the file. The file detail view now has a policy/encryption control.
- **Certificate expiry surfaced in the dashboard.** `GET /api/v1/cert-expiry` and the richer `GET /api/v1/health` were never called by the UI, so approaching expiry was visible only in server logs. The health section now shows a per-host card with days remaining and colour-coded status (ok / warning / expired), plus a near-expiry count tile.
- **Dead dashboard code removed or wired up.** `regenerateCert`, `startConfigApi`, `stopConfigApi` and the per-host `forceUpdate` / `clearForce` were unreachable duplicates of `renewCertAuto`, `createConfigApi`, `toggleConfigApi` and `toggleForce` — deleted, along with the unreferenced `showEditPins`. `createHostFetch` is now an "fetch from URL" tab on the add-host screen, `fetchBootstrapFromUrl` a button in the bootstrap section (for servers behind a TLS terminator), and new global force-update / clear-force buttons sit in the Config API general tab.
- **Enrollment tokens are shown once.** Generating a token now copies it to the clipboard and shows it in a one-time dialog (same flow as vault tokens); the list shows the masked prefix.

### Library — Post-update health gate now rolls back (G08)

- **A config that fails the post-update health check is rolled back instead of being left on disk.** `SSLCertificateUpdater.verifyPinnedConnection` had three branches: healthy → `Ready`, unhealthy → `Failed` *without touching the store*, exception → `configStore.clear()` + `httpClientProvider.reset()`. The third branch was unreachable: `DefaultCertificateConfigApi.healthCheck()` catches every exception and returns `false`, so the documented "on failure clears the config store and resets the client" never happened with the default API. The observable result was worse than a missing rollback: init reported failure while the new config stayed in the encrypted store, and the *next* cold start came up "Ready" on it — the second round returns `AlreadyCurrent`, which never reaches the gate at all. Unhealthy and threw are now the same outcome: the config that was in force before the update is restored to the store **and** to the live HTTP client, or, on a first install with nothing to fall back to, the store is cleared and the client returns to its fail-closed state. Re-saving the previous config also rewinds the persisted `issuedAt`, so the replay guard accepts the server's config again on the next attempt. Offline start-up is unaffected — the gate only runs after a config was actually applied (`UpdateResult.Updated`), never on the "backend unreachable" path that keeps running on the stored config. The KDoc now also states what the check really proves: it is a liveness check of the Config API over its bootstrap client, not a re-verification of the freshly installed target-host pins. Tests: `SSLCertificateUpdaterTest`.

### Library — Turning force-update off reaches the device (D04)

- **A cleared `forceUpdate` flag is now written to the stored config.** Change detection treated a raised flag as a change but not a cleared one, so a config whose only difference was `forceUpdate: true → false` was dropped as `AlreadyCurrent` and never rewritten — the stored copy kept `forceUpdate: true`. That is not cosmetic: `initializeAndUpdate` reads the *stored* flag on every cold start and fails with `ForceUpdateFailedException` when the backend is unreachable, so a device stayed unable to start offline after the operator had switched force off, until some unrelated pin version happened to bump. Clearing the flag deliberately does **not** produce `UpdateResult.Updated` — nothing about the pins changed and callers should not be told a new config was applied — but the flags are written back to disk on the already validated stored config (never an unvalidated remote payload), and the live client is left alone. Both the global and the per-host flag are compared. The in-memory config follows the disk (`HttpClientProvider.replaceConfigInPlace`, no client rebuild), so `isForceUpdate()` reports the cleared flag right away instead of after the next process start. Tests: `SSLCertificateUpdaterTest`.
- **`CertificateConfigStore` persists the per-host `forceUpdate` flag.** The stored entry format gained a trailing field (`hostname|version|hash1,hash2|forceUpdate`); entries written by earlier versions have three fields and load with `false`, which is also the fail-safe value. Without this the per-host half of the comparison above could never see anything but `false`. Tests: `CertificateConfigStoreTest`.

### Library — Vault file diagnostics

- **A blank vault access token is no longer sent as an empty header.** When `accessToken { … }` returned `""` — the normal state of a host app whose token store is still empty — `VaultFileRouter` sent `X-Vault-Token: ` anyway and the server answered "Invalid or revoked token", pointing operators at a revoked token that was never issued. Blank and whitespace-only tokens now omit the header, so the server reports the accurate "X-Vault-Token header required". Both are still HTTP 401; only the reason recorded in the server's distribution history changes. Tests: `VaultFileTokenHeaderTest`.
- **`VaultFileAccessPolicy.API_KEY` warns at build time.** The policy is satisfied with the server's admin `X-API-Key`, which the library deliberately never sends from a device (it would ship inside the APK), so a file declared this way silently fails with 401 on every fetch and the only trace is a `failed` row in the distribution history. `PinVaultConfig.Builder.build()` now logs one warning per such file, and the enum's KDoc says plainly that it is for server-side tooling only. The dashboard's vault upload form carries the same note next to the `api_key` option. Behavior is otherwise unchanged — the library still does not send the admin key.
- **Uncovered Config API ids warn at build time (M-07 follow-up).** The bundled backup rules exclude the stored pin config per file name, and Android's `<exclude>` takes no wildcards, so they can only name ids the library knows. An app registering its own `configApiId` had its `shared_prefs/ssl_cert_config_<id>.xml` included in cloud backup and device transfer, re-opening the pin-downgrade restore the exclusions exist to close. `PinVaultConfig.Builder.build()` now logs one warning per uncovered id, naming the exact `<exclude>` line to add; `configApi(...)`'s KDoc and both rule files carry the same warning. The library's own default id (`default`) was itself missing from the rules and has been added. The rules are otherwise unchanged: collapsing every scope into one preferences file would need a store migration, and the per-scope namespacing is itself what keeps two Config APIs' pins from colliding.

### Demo server — The vault switch actually switches something (C09)

- **`GET /api/v1/vault/{key}` refuses with 403 while the scope's `vault_enabled` is off.** The flag was written and read by two admin endpoints and consulted by nothing else, so "vault enabled" was a dashboard checkbox with no effect — an operator who noticed a file had gone out by mistake had no way to stop distribution short of deleting it. The download route now reads the flag per request (so the toggle takes effect without restarting the listener) and answers 403 for every key, present or absent, so a disabled vault does not reveal which keys it holds. Vault **administration** in that scope is deliberately unaffected — upload, list, policy, delete, tokens and distribution history stay reachable, because inspecting and cleaning up is exactly what follows flipping the switch. The flag is an operator kill switch, not an authentication boundary; per-file `access_policy` remains what guards content.
- **The default Config API has a `config_apis` row.** `default-tls` is mounted directly by `Main.kt` rather than through `POST /api/v1/config-apis/start`, so it never had a registry row, and `PUT /api/v1/config-apis/default-tls/vault-enabled` answered 404 — the switch was unusable on the one scope the sample app talks to. New `ConfigApiRegistry.ensureRegistered` registers it at boot and preserves an existing row's `vault_enabled`.
- **Restarting a Config API no longer re-enables its vault.** `POST /api/v1/config-apis/start` persisted the API with `INSERT OR REPLACE`, which deletes and re-inserts the row and therefore reset `vault_enabled` to its column default (1). It now goes through `ConfigApiRegistry.ensureRegistered`, which updates only port and mode.
- **The dashboard's vault toggle reflects the server's answer.** A rejected `PUT` left the checkbox in the position the operator had clicked, showing "vault disabled" for a vault that was still serving files; the toast did not carry the status code either. The checkbox now reverts on failure and the toast names the HTTP status.
- Tests: `VaultEnabledSwitchTest`. `openapi.yaml` updated — the previous text ("dashboard state only") described the old behavior.

### Known limitations (documented, not changed)

- **A failed enrollment still consumes its token.** `POST /api/v1/client-certs/enroll` generates the certificate and marks the enrollment token used before the response reaches the device; if the device then rejects the P12 (for example a missing `X-P12-SHA256` header) the token is spent and the operator has to issue a new one. Recording consumption only after a device-confirmed install would need a second round trip (a confirm/ack endpoint) and a way to expire never-confirmed certificates — out of scope here; see `SERVER_IMPLEMENTATION_GUIDE.md`.

## 2.0.0 — 2026-04-17

**PinVault 2.0 — Multi-Config-API + Vault Scoping + Per-File Security.**

### Config / DSL

- **Multi-Config-API DSL**. `PinVaultConfig.Builder()` accepts one or more
  `.configApi(id, url) { … }` blocks. Each block has its own bootstrap pins,
  TLS/mTLS pipeline, and endpoint paths. Vault files bind to a specific
  block via `.vaultFile(key) { configApi(id); … }`.
- **Per-file access policies**: `PUBLIC`, `API_KEY`, `TOKEN`, `TOKEN_MTLS`.
  `TOKEN` is the default — admin issues per-(device, file) tokens via
  `POST /api/v1/vault/{key}/tokens`. Replaced or revoked tokens invalidate
  immediately.
- **End-to-end encryption**: `encryption(VaultFileEncryption.END_TO_END)`
  wraps content with the device's Android-Keystore-backed RSA 2048 key
  (StrongBox when available) using RSA-OAEP-SHA256 + AES-256-GCM hybrid.
- **Server-side pin scoping**: `wantPinsFor(...)` + per-device
  `device_host_acl` table. Server returns only pins for hostnames the
  device is authorized to see; unauthorized requests logged.

### Library

- **`VaultFileDecryptor`**: pure JCA decryption of E2E envelopes (no
  Android deps — runs in Robolectric and plain JVM).
- **`DeviceKeyProvider`**: Android Keystore backend + software fallback.
- **`ConfigApiClient` + `VaultFileRouter`**: internal runtime that routes
  each vault fetch to the correct per-block client. Per-Config-API
  `CertificateConfigStore` namespaces pin storage to prevent cross-API
  hostname collisions.
- **`CertificateConfigApi`** gained three new methods with default
  implementations:
  - `fetchScopedConfig(currentVersion, hosts, deviceId)` for pin scoping
  - `downloadVaultFileWithMeta(endpoint, currentVersion, deviceId, accessToken)`
    for policy + encryption support
  - `registerDevicePublicKey(deviceId, publicKeyPem)` for E2E
- **`VaultFileConfig`** gained `configApiId`, `accessPolicy`,
  `accessTokenProvider`, `encryption` fields.

### Demo server

- **Flyway V2 migration**: drops and recreates `vault_files` and
  `vault_distributions` with `config_api_id` scoping. Adds four new tables:
  `vault_file_tokens`, `device_public_keys`, `device_host_acl`,
  `default_host_acl`. Adds `config_apis.vault_enabled` column.
- **New stores**: `VaultFileTokenStore`, `DevicePublicKeyStore`,
  `DeviceHostAclStore`.
- **New services**: `VaultEncryptionService` (RSA-OAEP + AES-GCM hybrid),
  `VaultAccessTokenService` (SHA-256 hashed, constant-time validation).
- **`vaultRoutes(configApiId, …)`**: every route Config-API-scoped.
  Enforces access policy (public / api_key / token / token_mtls) and
  applies end-to-end encryption when configured.
- **`CertificateConfigRoutes`**: accepts `?hosts=` parameter, intersects
  with `device_host_acl`, logs unauthorized host requests.
- **`AdminVaultRoutes`**: `PUT /config-apis/{id}/vault-enabled`,
  per-device + default host ACL CRUD endpoints.

### Web UI

- File list shows access policy badge + encryption indicator.
- Upload dialog has policy/encryption dropdowns; default is `token` + `plain`.
- File detail page includes a **Token Management** card (list + issue token
  modal that shows plaintext once + revoke).
- Config API detail page has a **Vault (V2)** section with vault-enabled
  toggle and a "Cihaz ACL yönet" button opening the ACL manager (default
  ACL editor + per-device ACL editing).

### Demo app

- **New `VaultSecurityDemoActivity`** demonstrating multi-API + 3 files
  across public / token / E2E policies, with a token editor dialog.
- `VaultFileDemoActivity` and `BaseDemoActivity` migrated to the new DSL.

### Security

- Default vault file policy is `token` — unauthenticated fetch is no longer
  the path of least resistance. `public` must be explicitly chosen.
- Token plaintext is generated from `SecureRandom` (32 bytes → URL-safe
  base64), returned once, stored as SHA-256 only, validated with
  `MessageDigest.isEqual` (constant-time).
- `token_mtls` requires both a matching token and an mTLS cert whose CN
  equals `X-Device-Id`. Token leak alone does not grant access.
- Device RSA private key stays in Android Keystore; server never sees it.

### Compatibility

- **Kotlin 1.9 consumer support**. Library is still compiled with Kotlin
  2.1, but `apiVersion` and `languageVersion` are now pinned to `1.9` so
  the emitted metadata is readable by Kotlin 1.9.x compilers.
- **Coroutines downgraded** `kotlinx-coroutines-android` `1.9.0` → `1.8.1`
  (and `kotlinx-coroutines-test` to match). The `1.9.0` artifact ships
  Kotlin 2.0 metadata, which Kotlin 1.9.x consumers cannot read; since
  PinVault's public API exposes `suspend` functions (`init`, `updateNow`,
  `enroll`, `fetchFile`, `syncAllFiles`, …), the coroutines metadata is
  reachable transitively and must also be 1.9-compatible.
- Fixes `Unable to read Kotlin metadata due to unsupported metadata
  version` (and `unsupported metadata kind: null`) on consumer projects
  using Kotlin 1.9.x.
